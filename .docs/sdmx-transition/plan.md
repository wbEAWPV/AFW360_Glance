# Plan: AFW 360 data standard v0.6, SDMX 3.1 conformance

Status: approved design, ready for orchestration. Written 2026-09-29 by Claude Fable 5.1 after four research passes (see `research/`) and eleven decisions taken by the data lead in conversation.

Branch: `standard/v0.6-sdmx`, cut from `dev/eb`. Merged back into `dev/eb` at Gate 3, when every work package is verified and the data lead accepts.

Companion files in this folder:

- `handover.md`: instructions for the orchestrator agent that runs this plan.
- `PROGRESS.md`: the live status log the orchestrator maintains.
- `sdmx-ml-cheatsheet.md`: exact SDMX-ML 3.1 element names, orders and rules, distilled from the schemas.
- `research/R1..R4`: the research reports (structures, tooling, global codelists, repository inventory). Agents read named sections only, never whole files.

## 0. Summary

The project's data standard v0.5 already follows the SDMX information model in spirit. This plan makes the files themselves SDMX 3.1 conformant while keeping CSV as the working format:

- Data files become **SDMX-CSV 2.1** data messages (three fixed leading columns, one column per DSD component, `NaN` for intentionally missing values).
- Reference metadata (surveys, sources, dashboard text, figures) becomes **SDMX-CSV 2.1 metadata messages**, generated from the existing registry CSVs.
- Structural metadata (agency, concepts, codelists, DSD, dataflow, MSD, metadataflow, provider schemes, provision agreements) is generated by R from the CSVs under `metadata/` into **one SDMX-ML 3.1 structure message**. No SDMX-JSON anywhere.
- The CSVs under `metadata/` remain the source of truth. A reverse importer turns an SDMX-ML export (for example from Fusion Metadata Registry after editing) back into the CSVs, so FMR can be used as an editor and validator.
- The dashboard reads the new files through one loader and stops reading `data_raw/`.
- The standard is revised to v0.6, metadata to 0.3.0, with every decision recorded (D27 to D46) and a conformance checklist with evidence.

Nothing under `data_raw/` changes. Every number in `data/` stays the same; the converter regenerates the files in the new layout and the independent reconciliation proves it.

## 1. Decisions taken (D27 to D46)

The data lead took D27 to D37 in conversation on 2026-09-29. D38 to D46 are design decisions this plan makes to carry those out; the data lead can veto any of them at Gate 1.

| Id | Decision | Why |
|---|---|---|
| D27 | Target the SDMX 3.1 family: SDMX-CSV 2.1.0 for data and reference metadata, SDMX-ML 3.1.0 for structures. | "Latest standard" as of 2026-09: IM 3.1 (2025-03), ML 3.1.0 and JSON 2.1.0 (2025-05), CSV 2.1.0 (2025-08). |
| D28 | The CSVs under `metadata/`, `content/` and `data/` are the source of truth. SDMX-ML is generated, committed, and checked for staleness like the generated doc tables (D20). | SDMX has no CSV format for structures; hand-editing XML is not acceptable; generated output with a staleness check is the pattern the project already uses. |

Alignment is by value where the project code rule allows, otherwise by a `GLOBAL_CODE` annotation. Global lists cannot be referenced or extended because they carry legacy (non-semver) versions and SDMX forbids a semver artefact from referencing a legacy-versioned one. | Codes are all DRAFT so renames are free; data files are regenerated by the converter. |
| D33 | Nine measures: `OBS_VALUE`, `STD_ERR`, `CI_LOWER`, `CI_UPPER`, `N_OBS`, `N_POP`, `N_OBS_NUM`, `DEFF`, `DF`. The five former reliability attributes become measures; three new optional measures are added. | SDMX 3.x observations carry several measures; a numerator count, design effect and degrees of freedom are not derivable and matter for reliability. Legacy files leave all but `OBS_VALUE` empty. |
| D34 | Add a `FREQ` dimension, first, always `A`, coded by a project `CL_FREQ` aligned to SDMX `CL_FREQ`. | SDMX convention for a DSD with a time dimension; matches World Bank DSDs. |
| D35 | FMR round-trip without Docker: Tomcat 10.1 plus the FMR 12 WAR on the installed Java 21, with a database. | D38 | `ACTION` is `R` (replace) in every published data file. | A published country-year-estimation file is the complete replacement of that slice; `R` is the action the SDMX-CSV guide recommends for full data responses and exists in both CSV 2.0 and 2.1. `I` is deprecated in 2.1. |
| D39 | `OBS_VALUE` is `NaN` on rows whose `OBS_STATUS` is `O` or `M`. Any other measure or attribute that a source cannot supply is left empty (omitted). | SDMX-CSV 2.x: empty means "not provided", `NaN` means "intentionally missing" for a numeric measure. |
| D40 | Every SDMX artefact carries the version in `metadata/VERSION` (`0.3.0`). | D41 | Codelist CSV columns map to SDMX by convention: `code` to id, `name_en` to name (en), `definition_en` to description (en), `parent` to the SDMX parent, `global_urn` to annotation `GLOBAL_CODE`, and every other column to an annotation of type `AFW_<COLUMN>` (upper case) whose value is the cell text. | D42 | Sentinels `_T` and `_Z` are added by the generator as real codes ("Total", "Not applicable") to every codelist whose dimension admits them (per the DSD's `sentinel` column), and stripped again by the importer. They still never appear in the CSV codelists. | SDMX validators only accept values that exist in the codelist; the global lists carry `_T` and `_Z` as codes too. |
| D43 | Registries become codelists plus metadatasets: `SERIES_PLAN.csv` derives `CL_SERIES`, `SOURCES.csv` derives `CL_SOURCE`, `SURVEYS.csv` derives `CL_SURVEY`, `FIGURES.csv` derives `CL_FIGURE` (id and name only). Their descriptive columns travel as metadata attributes of the MSD `MSD_AFW360`, one metadataset per row, targeting the code. `TEXT.csv` rows are metadatasets targeting the country code. Manifests stay a project-level sidecar. | Gives `SERIES_ID`, `SOURCE_ID` real codelists (resolving inventory inconsistency 15) and puts documentary metadata where SDMX puts it. A manifest describes a file, which is not an SDMX artefact. |
| D44 | `metadata/structure/ARTEFACTS.csv` lists every SDMX artefact to generate: id, type, agency, source file, name, description, status. The generator iterates over it. | Names and descriptions of artefacts need a home; the list of what to generate should be data, not code. |
| D45 | Project-only metadata (`TAB_PLAN`, `SERIES_PLAN`, `RULES`, `INDICATOR_QUALIFIERS`, `QUALIFIER_PAIRS`, `LEGACY_*`, `COLUMNS`, `DSD_AFW360_HH.csv`, manifests) stays CSV and is documented as tooling metadata outside SDMX. No VTL, no DataConstraint in this release. | SDMX cannot express required coverage or arithmetic rules; the project validator keeps that job. A DataConstraint for allowed content is a later option. |
| D46 | Data file column order follows the DSD: fixed columns, dimensions, `TIME_PERIOD`, measures, attributes. 37 columns, 19-column key. | SDMX-CSV recommends component order as in the DSD. |

## 2. Target design

### 2.1 Identity and versioning

- Agency `WB.AFW360`. Declared by a `WB:AGENCIES` agency scheme (fixed id, no version attribute in XML) containing `Agency id="AFW360"`, name "West Africa Micro Data 360 (AFW DIP/POV team)".
- Every maintainable artefact: `agencyID="WB.AFW360"`, `version="0.3.0"` (from `metadata/VERSION`).
- URN form: `urn:sdmx:org.sdmx.infomodel.<package>.<Class>=WB.AFW360:<ID>(0.3.0)`; codes append `.<CODE>`.
- Short reference form used in CSV messages: `WB.AFW360:<ID>(0.3.0)`.
- Message header sender id: `WB_AFW360` (sender ids are plain IDs and cannot contain a dot).
- Artefact ids are NCNames: start with a letter, then letters, digits, `_` or `-`. Project code rules (upper case, at most 32 characters, no leading `_` except sentinels) are stricter and stay.

Header and first row of `data/AFW360_HH_SEN_2021_SURVEY.csv` after the change (one line each; shown wrapped):

```

0.01,,,,,,,,,
AGR_CULTIVATES,SHARE,0.01,A,SEN_EHCVM2021_LEGACY_v1,
```

Rules:

- 37 columns in this order (D46). The key is the 18 dimensions plus `TIME_PERIOD` (19 columns).
- `STRUCTURE` is always `dataflow`; `STRUCTURE_ID` is `WB.AFW360:AFW360_HH(<VERSION>)`; `ACTION` is `R` (D38).
- `FREQ` is `A`.
- `OBS_VALUE` is `NaN` when `OBS_STATUS` is `O` or `M`; otherwise a number (D39). Other measures and optional attributes are empty when not available.
- Numbers use `.` as decimal separator, no thousands separator; unchanged.
- RFC 4180 quoting (readr does it). UTF-8 without BOM, LF line endings (project convention; RFC 4180 names CRLF but SDMX-CSV does not require it; documented).
- File names unchanged.
- Manifest keys: `dataflow` becomes `structure_id` (`WB.AFW360:AFW360_HH(0.3.0)`); a new key `sdmx_csv_version` = `2.1.0`; the other 15 keys unchanged.

### 2.5 Codelists and the CSV-to-SDMX mapping

Every `metadata/codelists/CL_*.csv` becomes a codelist `WB.AFW360:CL_*(0.3.0)`. Mapping (D41):

| CSV column | SDMX |
|---|---|
| `code` | `Code/@id` |
| `name_en` | `Name xml:lang="en"` |
| `definition_en` | `Description xml:lang="en"` (omitted when empty) |
| `parent` | `Parent` (same codelist) |
| `global_urn` | annotation type `GLOBAL_CODE`, value = the URN |
| `status`, `version_added`, `replaced_by`, `notes` | annotations `AFW_STATUS`, `AFW_VERSION_ADDED`, `AFW_REPLACED_BY`, `AFW_NOTES` |
| any other column | annotation `AFW_<COLUMN upper-cased>`, value = cell text as is (space-separated lists stay space-separated) |

Annotation form: `Annotation id="<type>"` with `AnnotationType` = type and `AnnotationValue` = value. Annotations are the first child of the code. Empty cells produce no annotation.

Special cases:

- `CL_GEO_SCHEME.csv` is keyed by `ref_area` + `code`; the SDMX code id is `<ref_area>_<code>` (for example `SEN_ADM1`) with the two parts also kept as annotations. The importer splits on the first underscore.
- Sentinels (D42): the generator appends `_T` ("Total") and `_Z` ("Not applicable") to `CL_GEO` (`_T`), `CL_SEX` and `CL_AGE` (`_T`, `_Z`), `CL_URBANISATION` (`_T`), `CL_COMP_BREAKDOWN` (`_T`), `CL_QUALIFIER` (`_Z`), reading the DSD CSV's `sentinel` column. Each carries `GLOBAL_CODE` pointing at `SDMX:CL_SEX(2.1)._T` or `._Z` and an annotation `AFW_SENTINEL` = `Y`, which the importer uses to drop them.
- Derived codelists (D43): `CL_SERIES` from `plans/SERIES_PLAN.csv` (one code per distinct `series_id`, name = `name_en` of the `ALL` row, annotations `AFW_STATUS` from the `ALL` row); `CL_SOURCE` from `registries/SOURCES.csv` (name = `source_id`, description = `notes`); `CL_SURVEY` from `surveys/SURVEYS.csv` (name = `survey_name`); `CL_FIGURE` from `registries/FIGURES.csv` (name = `title_en`). Derived codelists carry only id, name, description and `AFW_STATUS`; everything else goes to metadatasets (2.7).
- Every maintainable carries annotations `AFW_SOURCE_FILE` (repository path of the CSV it was generated from) and `AFW_METADATA_VERSION`.
- Codelist names and descriptions come from `ARTEFACTS.csv` (D44).

### 2.6 Concept scheme `CS_AFW360`

One concept per component id of 2.4 (`FREQ`, `REF_AREA`, ..., `OBS_COMMENT`; the five `COMP_BREAKDOWN_n` and five `MEASURE_QUAL_n` are separate concepts), plus one concept per metadata attribute of 2.7. Concept name and description for components come from the DSD CSV (`name_en`, `description`); for metadata attributes from `COLUMNS.csv` (`column` humanised as name, `description` as description). A concept that matches an SDMX cross-domain concept carries annotation `SDMX_CROSS_DOMAIN_CONCEPT` with the concept id in `SDMX:CROSS_DOMAIN_CONCEPTS(2.0)`: `FREQ`, `REF_AREA`, `TIME_PERIOD`, `OBS_VALUE`, `OBS_STATUS`, `UNIT_MEASURE`, `SEX`, `AGE`, `INDICATOR`, `OBS_COMMENT` (to `COMMENT`), `SOURCE_ID` (to `DATA_SOURCE`). Core representation: coded concepts reference their codelist; numeric ones carry the `TextFormat` of 2.4; text ones `String`.

### 2.7 Reference metadata

- MSD `WB.AFW360:MSD_AFW360(0.3.0)` with four presentational parent attributes, each with one child per source column (minus the id and `status` columns), all `String`, `minOccurs=0`:
  - `SURVEY`: children from `SURVEYS.csv` columns 2 to 24 (`REF_AREA`, `TIME_PERIOD`, `SURVEY_NAME`, ... `NOTES`); ids are the column names upper-cased.
  - `SOURCE`: from `SOURCES.csv` columns 2 to 13.
  - `TEXT`: `SLOT`, `REF_AREA`, `TIME_PERIOD`, `ORDER`, `TITLE`, `BODY`, `UPDATED_ON`. `BODY` holds the Markdown source: the `body` cell, or the content of the `file` when set.
  - `FIGURE`: from `FIGURES.csv` columns 2 to 16 (`REF_AREA` ... `NOTES`, excluding `figure_id` and `status`).
- Metadataflow `MDF_AFW360` with structure `MSD_AFW360` and targets that cover every metadataset target below (wildcard URNs; the implementer confirms the exact wildcard syntax against the XSD `WildcardUrnType` and records it).
- `MetadataProviderScheme` `METADATA_PROVIDERS` (agency `WB.AFW360`) with provider `AFW_POV`; `MetadataProvisionAgreement` `MPA_AFW360` (metadataflow + provider).
- Metadatasets, one per registry row, written as SDMX-CSV 2.1 metadata messages (header `MDSTRUCTURE,MDSTRUCTURE_ID,METADATASET_ID,TARGET_TYPES,TARGET_IDS,<attribute columns>`; nested attribute headers dotted, for example `SURVEY.SURVEY_NAME`):
  - `MDS_SURVEYS.csv`: `METADATASET_ID` = `WB.AFW360:MDS_SURVEY_<survey_id>`; target the code `WB.AFW360:CL_SURVEY(0.3.0).<survey_id>`.
  - `MDS_SOURCES.csv`: target `CL_SOURCE` code.
  - `MDS_TEXT.csv`: id `MDS_TEXT_<slot>_<ref_area>_<time_period>_<order>`; target the country code `WB.AFW360:CL_AREA(0.3.0).<ref_area>`.
  - `MDS_FIGURES.csv`: target `CL_FIGURE` code.
  - `MDSTRUCTURE` = `metadataflow`, `MDSTRUCTURE_ID` = `WB.AFW360:MDF_AFW360(0.3.0)`. Metadatasets are non-versioned (no version in the id).
  - The short-form syntax for an item target in `TARGET_IDS` is not spelled out in the SDMX-CSV metadata guide. The implementer uses `AGENCY:CODELIST(VERSION).CODE` with `TARGET_TYPES` = `codelist`, confirms that pysdmx reads it back with the intended target, and records the outcome in `PROGRESS.md`. If it cannot be confirmed, metadatasets target the dataflow `WB.AFW360:AFW360_HH(0.3.0)` and the key columns already inside the attributes identify the row; the standard documents whichever form is used.

### 2.8 Providers and provision

`DataProviderScheme` `DATA_PROVIDERS` (agency `WB.AFW360`, fixed version) with provider `AFW_POV` ("AFW DIP/POV team"); `ProvisionAgreement` `PA_AFW360_HH` linking the dataflow and the provider. Both are cheap and let FMR validate data under a provision agreement later.

### 2.10 Metadata changes, 0.2.0 to 0.3.0 (migration script)

## 5. Risks and contingencies

| Risk | Signal | Response |
|---|---|---|
| FMR 12.4 rejects SDMX-ML 3.1 namespaces | import error at WP8b | `--sdmx-ml-version 3.0` profile (2.13); canonical file stays 3.1 |
| FMR cannot run without Docker on this machine (database) | WP8a finds no portable database | Gate 2 defers; WP8c documents; files stay loadable |
| SDMX-CSV metadata item-target syntax unconfirmed | pysdmx reads a different target | dataflow target fallback (2.7); documented |
| `TIME_PERIOD` not accepted in an attribute relationship | XSD error | not used in this design (only observation, dimension groups without time, dataflow) |
| Global age-band ids do not match the project's bands | WP2 lookup | keep project codes, `global_urn` empty, note in CHANGELOG |
| Dashboard numbers change after switch-over | WP9b regression script | the only intended changes are Guinea-Bissau reading its own data and formatting; anything else is a defect to fix before commit |
| Agent context overrun | implementer report exceeds budget or degrades | split the WP along the file lists; never widen context |
| Test suite runtime | slow full runs | run the relevant test file during development, the full suite only for verification |
