## Deviations           (what the card said, what you did, why)
- The card's fixture-building formula ("every `POV_NUM` child gets 1000000 and its parent 1000000 × k") only works for one non-`TOTAL` cut at a time: `AGG_SUM`'s parent is the single `TOTAL`-cut row, shared by every cut, and the real `TAB_PLAN`'s non-`TOTAL` cuts (`URB`, `HHH_SEX`, `HHH_AGE`, `QUINT`, `ADM1`, `ZONES`) have different child counts `k`, so one parent value cannot satisfy "sum of children" for all of them simultaneously. My tests build each fixture on a *temporary copy* of the real metadata (`make_temp_root()`) with `TAB_PLAN.csv` trimmed, via `edit_csv()`, to `TOTAL` plus exactly one other cut (`URB`, k=3, for most tests; `ZONES`, k=6 for SEN, for the two tests whose numbers the card states directly — this also confirms my tolerance formula reproduces the card's own 35000). The real `TAB_PLAN.csv` is untouched.
- `AGG_BRACKET`, `SUM_TO_1_QUAL` and `SUM_TO_1_BRK` are unaffected by this (a bracket/closure check is satisfied by equal values regardless of how many cuts exist), so this trimming only mattered for `AGG_SUM`'s consistent-fixture construction.
- `EQUALS_NPOP_RATIO`'s "filled" formula is not fully specified by the card beyond "check ... the ratio within the sum tolerance." No indicator in the real `CL_INDICATOR.csv` currently carries `AGG_NPOP_MEAN` or `EQUALS_NPOP_RATIO` (confirmed via `table(CL_INDICATOR$checks)`), so this branch is unexercised by real data and untested by any WP13.A* check. I implemented the "N_POP empty → one INFO per file and token" half fully (well-specified, matches AGG_BRACKET's own note that it "stands in for a weighted-mean check when N_POP is absent"), and `AGG_NPOP_MEAN`'s "filled" half as the literal weighted mean vs. parent (well-defined from AGG_BRACKET's own cross-reference). For `EQUALS_NPOP_RATIO`'s "filled" half I assumed `value == N_OBS/N_POP`, the most literal reading of "ratio," but flag this as an assumption — see Questions.

## Questions            (contract doubts, and anything only the user can decide)
- **Manifest format mismatch (affects every wave-3 package that uses `make_data_fixture()` for a `ROUNDED_2DP` test):** `contract/csv_headers.csv` declares `AFW360_HH_<ISO3>_<YEAR>_manifest.csv` as 2 columns, `key`/`value` (a long key-value file), and `pipeline/R/ctx.R`'s `build_ctx()` reads it that way (column 1 = key, column 2 = value, one row per key). But `pipeline/tests/testthat/helper-data-fixture.R`'s `make_data_fixture()` writes the manifest as **one row of 16 named columns** (`dataflow`, `dsd_version`, ..., `precision`, ...). Read the long-format way, that one wide row becomes a single key/value pair — the first two column *names*/*values* (`"dataflow"` → `"AFW360_HH"`) — so `ctx$precision[[key]]` always resolves to the default `"EXACT"`, never the fixture's actual `"ROUNDED_2DP"`, regardless of what `make_data_fixture()` intended. I could not fix this myself (`ctx.R` is WP11's, `helper-data-fixture.R` is a shared wave-2 test helper, neither is in WP13's Owned outputs), so my tests rewrite the manifest into the long `key`/`value` format after calling `make_data_fixture()`, in the test file only. Any other wave-3 package's tests that call `build_ctx()` on a `make_data_fixture()` output and check `ROUNDED_2DP`-specific behavior will hit the same silent `EXACT` fallback unless they do the same.
- **`TAB_PLAN`'s `AEZ` cut has no `ref_area` scoping, but `CL_GEO` has no `AEZ` codes for `SEN`:** `required_rows(meta, "SEN", "2021")` on the real, unmodified metadata stops with an error ("no CL_GEO codes for ref_area=SEN scheme=AEZ") the moment `TAB_PLAN`'s `AEZ` cut row (`ref_area = ALL`) is reached, because `CL_GEO.csv` only has `ADM0`/`ADM1`/`ZONES` rows for `SEN`. My tests never build a fixture with the real, untrimmed `TAB_PLAN` for this reason. This will very likely also stop the wave-3 integrator's real-data run for SEN, or WP15's converter, unless `AEZ`'s `TAB_PLAN` row is scoped to the country that actually has `AEZ` geo codes (from the original dashboard's per-country sheet list, this sounds like it should be GNB-only, with `SEN` using its own `ZONES` scheme for the equivalent breakdown) — worth flagging to whoever owns `TAB_PLAN`/`CL_GEO` (WP05/WP08) or the wave-3 integrator.
