# WP13 — Validator: verification rules

- **Wave:** 3. **Depends on:** wave 2 merged. **Slug:** `validator-rules`. **Acceptance script:** `pipeline/acceptance/wp13_validator-rules.R`.

## Goal

The checks that make the numbers trustworthy: totals that add up, shares that close to 1, poverty rates that rise with the line. Each indicator declares its rules in `CL_INDICATOR.checks`.

## Read (exactly this)

- `packages/COMMON.md` and this card.
- The function signatures in `pipeline/R/io.R`, `ctx.R` and `plan.R`, and in the two test helpers. Use `grep -n "function("`.
- Through R: `table()` of `CL_INDICATOR$checks`, and `head()` of `SERIES_PLAN`, `TAB_PLAN` and `LEGACY_LABELS`.

## Owned outputs

`pipeline/R/validate_rules.R` and `pipeline/tests/testthat/test-validate-rules.R`.

## Interface

- Your functions are named `vc_rule_<check>(ctx)`.
  - Each returns a tibble with the columns `check_id, severity, file, row_key, message`. Zero rows means pass.
  - `ctx` is the list from `build_ctx()`.
  - `check_id` is `RULE.<NAME>`.
- `pipeline/validate.R` (WP11, built at the same time as your package) finds your functions by name. Do not write an entry point.
- With no data in `ctx`, every function returns zero rows.

**Findings format** (word for word the same on the cards WP11 to WP14):

- `file` is the path relative to the root, with forward slashes.
- `row_key`:
  - for a data row, the 18 key values joined by one space;
  - for a row of a metadata or content CSV, `<column>=<value>` of the column or columns that identify the row, joined by one space (`code=URB`, or `ref_area=GNB sheet=ZAE column=estimateEst`);
  - for a feature of a GeoPackage, `layer=<layer> geo_code=<code>`;
  - empty for a finding about a whole file.
- The cap: when one check has more than 20 findings for one file, keep the first 20 in `row_key` order, and add one finding with the same `check_id` and severity, an empty `row_key`, and the message `SUMMARY: <n> findings in total, 20 shown`.

## Rules you need

**Provenance.** Join each data file to `required_rows(meta, REF_AREA, TIME_PERIOD)` on the 18 key columns. This gives every row its `series_id` and its `cut_id`. Ignore rows that do not join; the coverage check reports them.

- The **parent** of a row is the row of the same series in the cut `TOTAL` (gap h).
- The **children** of a parent in a cut are the rows of that series in that cut.
- The number of children a cut should have, `k`, comes from `required_rows()`, not from the file.

**Tolerance** (gap h).

- For a file with `precision = ROUNDED_2DP`: `h = 0.005 × scale`, where `scale` is the series' `LEGACY_LABELS.scale`, 1 when it is absent.
  - A sum of `k` children against its parent tolerates `(k + 1) × h`.
  - A closure over `k` categories tolerates `k × h`.
  - A bracket tolerates `h` on each side.
- For an `EXACT` file: `h = 0`, and sums tolerate `1e-6 × max(1, |parent|)`.
- Every comparison is `abs(deviation) <= tolerance + 1e-9`.
- Monotonicity gets no tolerance.

**Incomplete groups.** When a child is missing (withheld), or has `OBS_STATUS` `O` or `M`, the aggregation check for that parent and cut is skipped, with one `WARN` finding `RULE.AGG_SKIPPED`. When a closure's categories are not all present in the plan, it is skipped with one `INFO` finding per indicator and variable (`RULE.CLOSURE_PARTIAL`), not one per cell.

**The checks,** one per token of `CL_INDICATOR.checks`. The field holds tokens separated by one space (`RANGE_0_1 AGG_BRACKET SUM_TO_1_OVER:COICOP`); split on spaces only, and then split a token at its first `:` to get the argument.

| Token | `check_id` | Rule |
|---|---|---|
| `RANGE_0_1` | `RULE.RANGE_0_1` | The value lies between 0 and 1. |
| `RANGE_NONNEG` | `RULE.RANGE_NONNEG` | The value is at least 0. |
| `AGG_SUM` | `RULE.AGG_SUM` | For every series and every cut other than `TOTAL`, the children sum to the parent within `(k + 1) × h`. All eight legacy cuts are partitions. |
| `AGG_BRACKET` | `RULE.AGG_BRACKET` | The parent lies within [min child − h, max child + h]. This stands in for a weighted-mean check when `N_POP` is absent. |
| `SUM_TO_1_OVER:<QUAL_VAR>` | `RULE.SUM_TO_1_QUAL` | Group the indicator's rows by every key column, with the slot that holds a category of `<QUAL_VAR>` taken out. A group that holds every category of that variable (all of its `CL_QUALIFIER` rows) sums to `1 × scale` within `k × h`. A group with fewer categories is partial. For `CONS_SH`, the 13 COICOP rows of a cell close to 1; the rows that also carry an `ACQ_*` qualifier form their own partial groups. |
| `SUM_TO_1_OVER_BRK` | `RULE.SUM_TO_1_BRK` | Take the series of one indicator with the same qualifiers whose defining breakdowns belong to one variable. Within each cell of each cut, if every category of the variable (all of its `CL_COMP_BREAKDOWN` rows) is present, the values sum to 1 within `k × h`; otherwise the group is partial. `HE_COUNT`, `EMP_SECTOR` and `EMP_TYPE` are complete in the legacy data; `EMP_STATUS`, `EMP_ISIC`, `EMP_FORMAL`, `HEO_SEX` and `HEO_MSTAT` are partial. |
| `MONOTONE_IN:POVLINE` | `RULE.MONOTONE` | Among rows that differ only in their `POVLINE_*` qualifier, the value does not fall as the line's `CL_QUALIFIER.value` rises. Rows without a value are skipped. |
| `AGG_NPOP_MEAN`, `EQUALS_NPOP_RATIO` | `RULE.NPOP_SKIPPED` | These need `N_POP`. When `N_POP` is empty, give one `INFO` finding per file and token. When it is filled, check the weighted mean or the ratio within the sum tolerance. |
| `NONE` | — | No check. |

A token that is not in this table gives one `ERROR` finding `RULE.UNKNOWN_TOKEN` per indicator.

Keep findings few: apply the cap of the findings format.

## Steps

1. Implement the module: a small helper that returns the joined rows with their numeric value, scale and tolerance, and then one function per check.
2. Write the tests on a temporary copy of the real metadata, with a data file from `make_data_fixture()`.
   - Use the series `POV_NUM.POVLINE_PL300.PPP_2021`, `POV_NUM.POVLINE_PL420.PPP_2021`, `POV_HC.POVLINE_PL300.PPP_2021`, `POV_HC.POVLINE_PL420.PPP_2021`, the 13 plain `CONS_SH.COICOP_*` series, and the five `POP_HH_SH.HE_COUNT_*` series.
   - The fixture writes 0.5 everywhere, so your test first sets consistent values with one helper function, by rule, not by hand: every `POV_NUM` child gets 1000000 and its parent 1000000 × k (the values are in persons, and the legacy scale of `POV_NUM` is 1e6, so smaller numbers would hide inside the tolerance); every `POV_HC` row gets 0.2 for `PL300` and 0.4 for `PL420`; every `CONS_SH` row gets `fmt_num(1/13)` and every `POP_HH_SH` row `fmt_num(1/5)`. The fixture's manifest says `precision = ROUNDED_2DP`, so the tolerances absorb the rounding of 1/13. Then mutate one thing per test.

## Acceptance checks

- WP13.A1: on the consistent fixture, your functions return 0 `ERROR`.
- WP13.A2: each mutation below gives exactly its `check_id`:
  - one child of a `POV_NUM` parent doubled gives `RULE.AGG_SUM`;
  - a `POV_HC` parent set above every child plus `h` gives `RULE.AGG_BRACKET`;
  - one COICOP share raised so that the cell's sum is 1.2 gives `RULE.SUM_TO_1_QUAL`;
  - one `HE_COUNT` share raised so that the cell's sum is 1.2 gives `RULE.SUM_TO_1_BRK`;
  - `PL300` set above `PL420` in one cell gives `RULE.MONOTONE`;
  - a share set to `1.3` gives `RULE.RANGE_0_1`.
- WP13.A3: rounding noise does not fail. A COICOP cell that sums to 0.97 passes (tolerance 0.065). A `POV_NUM` parent of 3130000 with 6 children that sum to 3120000 passes (tolerance 35000).
- WP13.A4: at the boundary, a deviation of exactly the tolerance passes, and the tolerance plus 0.001 × scale fails.
- WP13.A5: a fixture with one child row deleted gives `WARN RULE.AGG_SKIPPED` and no `ERROR` for that parent and cut. The partial variable `EMP_STATUS` gives `INFO RULE.CLOSURE_PARTIAL` and no `ERROR`.
- WP13.A6: with `ctx$data` empty, every function returns zero rows. The unit tests pass.

## Verifier focus

Compute by hand the tolerance for one `AGG_SUM` case and one closure case, and confirm the pass/fail boundary with your own numbers. These rules were tested against the raw workbooks when the plan was written: with these tolerances, the real data break none of them. No real data files exist while this package is built (the converter, WP15, is built at the same time), so neither you nor the implementer runs the checks on real data: the wave-3 integrator does. If it reports an `ERROR` there, it points at the check or at the converter first.
