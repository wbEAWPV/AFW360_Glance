AFW 360 data standard and producer guidelines

Draft v0.3 · Proposal: no file described here exists yet

Published

September 21, 2026

This document defines how data for the West Africa Micro Data 360 platform (AFW 360) are structured, coded and documented, how producers create data files, and how the database is extended to new countries, indicators and breakdowns. It follows the SDMX information model (the ISO standard statistical agencies use to exchange data) and borrows the World Bank Data360 dimension layout, stored as plain CSV files in git.

Background on the current inputs is in input-tables-findings.qmd. Nothing here changes the current INPUT Tables/ files. A Python converter will produce the new files from them, and the dashboard will switch over later.

How to read this document. Section 1 is the whole idea on one page: the model, where every file lives, and how the database grows. Read it first. Sections 2 to 11 are reference material; come back to them when you need the exact rule. Section 12 records the design decisions already taken and those still open. Table 1 suggests where to start.

1 The idea in one page

This standard exists so that every country’s numbers arrive in the same shape. It is written for the country economists and data scientists who prepare indicators from household microdata, and it is what they work from when they add a country, an indicator or a new way of cutting the data. It is also the specification for the developers who build the converter, the validator and the dashboard on top of it.

The database it describes is meant to be a one-stop shop for country-level insight. Every indicator in it comes from national household microdata, and every number is stored the same way for every country.

1.1 One row is one number

Each row of a data file carries one value and the full set of codes that say what that value is: which country, which year, which population, which measure. Those codes fall into two families (Table 2), and telling them apart is the whole model.

The quickest test is the population. If the people behind the categories add up to the whole, as regions or quintiles do, the variable is a breakdown. If every category covers the same whole population again, as the $3.00 and $4.20 poverty lines do, it is a qualifier. N_POP, the population behind each row, makes the test mechanical.

This matters for three reasons. The poverty rate at any line and PPP round is one indicator, POV_HC, not one per line. Every population share is one indicator, POP_SH, not thirty. And a new grouping such as sector of employment is a row in a codelist, not a change to the file format.

This distinction is the foundation of the database. Every rule in the rest of this document follows from it, and everyone who adds data has to apply it consistently.

1.2 Common compositions, and how each number is checked

Table 3 builds some familiar numbers out of the two families. The last column shows what the coding buys in practice: once a number is coded this way, the validator can check it against related rows.

Everything in the last column reduces to three generic rules, and each indicator declares which of them apply in its checks field (Section 5.2):

  1. Aggregation. Over a partition, totals sum, and means and shares aggregate as N_POP-weighted averages.
  2. Closure. Some qualifiers partition the measured quantity: COICOP divisions sum to 1, and fiscal instruments sum to the total.
  3. Range and order. Shares lie in 0–1, counts are non-negative, and the headcount rises with the poverty line.

Section 2.7 shows these numbers as they are written in a data file.

1.3 Where everything lives

Everything is plain files in one git repository, in five top-level folders (Listing 1):

  • metadata/ is the dictionary. It says what every code means, which rows a data file must contain, and which surveys the numbers come from. Every other folder refers to it, and every change to it is reviewed (Section 10).
  • data/ holds the numbers: one CSV per country and reference year, each with a manifest recording how it was produced and against which metadata version.
  • geo/ holds the boundaries used for maps.
  • content/ and assets/ hold the prose and images the dashboard shows beside the numbers.

Numbers flow one way. A producer’s program computes indicators from the harmonized microdata and writes a data file and its manifest. The validator checks the file against metadata/ (Section 11). The dashboard reads published files through a single loader. Until producers deliver files, the converter does their job: it turns the current Excel tables into data files using LEGACY_LABELS.csv (Annex).

None of this exists yet; the dashboard still reads INPUT Tables/, INPUT shp/ and INPUT Text/ directly. The natural order of work is the metadata for Senegal and Guinea-Bissau first, then the converter, then the validator, and last the switch of the dashboard to the new loader, because each step needs the one before it.

1.4 How the database grows

The rule for every extension is metadata first, data last. A number can enter the database only once its codes exist, so every change starts in the codelists and ends with a data file that the validator accepts. If a new number cannot be described with the existing codes, the codes are extended first, in the same pull request as the data.

A new country is added in this order:

  1. Register the country in CL_AREA.
  2. Register its spatial schemes in CL_GEO_SCHEME and their units in CL_GEO.
  3. Check its indicators against the dictionary, CL_INDICATOR. Every country should produce the same set of indicators, matching the dictionary’s codes, definitions and meaning. When a country’s survey cannot match a definition, update the dictionary with a new code linked to the old one through related, rather than stretching an existing code to fit.
  4. Do the same for breakdowns and qualifiers: the country’s categories map to the shared codes in CL_COMP_BREAKDOWN and CL_QUALIFIER.
  5. Describe the survey in SURVEYS.csv, and add the boundary files the maps need.
  6. Produce the data file for each reference year, following TAB_PLAN, together with its manifest.

Section 7.4 gives each step in full.

A new indicator starts in the microdata, not in the aggregation. First standardize the variables it needs in the survey microdata itself, so that each one has the same definition, universe, unit and recall period in every country. Once they are standardized, the indicator is a simple aggregate of them: a mean, a share or a total over each cut. If an indicator needs complicated logic at the aggregation step, its variables are not yet standardized enough.

Every constructed variable also needs its own metadata, recording what the microdata looked like when the indicator was computed from it: the questionnaire module and questions, the recall period, the universe, the units and any recoding. CL_INDICATOR points to these variables through source_questionnaire, source_vars and program. Where the variable-level documentation itself is kept is still an open decision (Section 12.2).

Everything else, such as a breakdown, a qualifier, a poverty line, a spatial scheme, a survey round, a piece of text or a figure, is listed in Table 18 with the files to edit and the version bump it needs. The only structural change is to the columns of the data file, and only the data team makes it (Section 10).

2 Data structure: dataflow AFW360_HH

This section is the contract for the data file: its columns, what may go in each, and which rows it must contain. Read it before writing a producer program, the converter or the dashboard loader.

A dataflow is SDMX’s name for a family of files that share one set of columns and codelists. AFW360_HH covers everything estimated from household-survey microdata: poverty, consumption, jobs, enterprises, agriculture, energy, housing, shocks, social protection, inequality and fiscal incidence. Fiscal incidence is not a separate dataflow. It comes from the same households and the same cuts, and differs only in its qualifiers.

A separate dataflow is needed only when the statistical unit is not the household population at all, for example tax parameters by bracket or macroeconomic series. The rule is: new dimensions or different units mean a new dataflow; a new source or a new round means only a new file.

2.1 Columns

Data files have exactly the 26 columns in Table 4, in that order. The role says which family a column belongs to (Section 1.1): breakdowns say who is counted, qualifiers say what is measured, and attributes describe the value’s reliability and origin.

2.2 The two sentinels

_T and _Z are reserved codes with fixed meanings. They are never listed in a codelist, and no other code may start with them.

  • _T, total. The value covers every unit and is not split on this dimension. Valid in GEO, SEX, AGE, URBANISATION and the breakdown slots.
  • _Z, not applicable. Valid in every unused qualifier slot, and in SEX or AGE when the indicator is not about individuals. A household-level indicator writes SEX=_Z, not SEX=_T, because “total over both sexes” would be a claim about a dimension that does not apply to households.
  • GEO and URBANISATION are never _Z: every unit lives somewhere.

2.3 Rules for the breakdown columns

  1. Fill the slots from the left, with no gaps. Unused slots are _T.
  2. Use the canonical order. When a row has several breakdowns, they go in ascending slot_order from CL_BRK_VAR, with ties broken alphabetically by var_code. Each combination then has exactly one spelling.
  3. One category per variable per row.
  4. Respect unit compatibility. A breakdown variable may be used only with indicators whose stat_unit appears in its applies_to_units.
  5. Never duplicate a named dimension. Residence, individual sex, individual age and geography always go in their own columns.
  6. SEX and AGE describe the individual being counted, not the household head. The head’s characteristics are breakdown variables (HHH_SEX, HHH_AGE) and go in the slots.
  7. An age band that defines an indicator’s universe is not a breakdown. “Employed, 15–64” has that band in its universe and writes AGE=_T.

2.4 Rules for the qualifier columns

  1. Fill from the left, with no gaps. Unused slots are _Z.
  2. Use the canonical order: ascending slot_order from CL_QUAL_VAR, with ties broken alphabetically.
  3. One category per qualifier variable per row.
  4. A row may use only the qualifiers its indicator declares in CL_INDICATOR.qualifiers, plus any qualifier required by a breakdown it uses. POOR_Y requires a poverty line, so a food-share row broken down by poverty status carries POVLINE_* and PPP_* even though CONS_SH does not otherwise use them.
  5. Pairings must be allowed: CL_QUALIFIER.valid_with says which PPP rounds go with which line.

2.5 Values and attributes

  • Store OBS_VALUE unrounded, with . as the decimal separator and no thousands separator or % sign. Rounding is a display decision (display_as, decimals).
  • Use base units. Shares are 0–1, never 0–100. People are counted in persons, not millions. Money is in whole currency units.
  • Do not suppress. Every estimate is published whatever its sample size. Reliability travels with the value instead: N_OBS and N_POP are required on every row, STD_ERR and the confidence interval on every row whose statistic admits them, and the dashboard shows them (Section 6.3).
  • N_OBS is the unweighted number of records of the estimation file used: records in the group, in the indicator’s universe, with a non-missing value. When a person-weighted poverty rate is computed on a household file, N_OBS counts households. SURVEYS.analysis_units records which file each stat_unit is estimated from, so a reader always knows what N_OBS counts.
  • N_POP is the sum of weights over those same records: the population, households or enterprises the value refers to.
  • Standard errors and confidence intervals must reflect the survey design (weights, strata and PSUs, with linearized variance). Intervals are at 95%.

OBS_STATUS takes one of the four codes in Table 5, which come from the SDMX cross-domain CL_OBS_STATUS. A cell that can never exist is normally declared in the indicator’s excluded_breakdowns (Section 5.2) and left out of the file. M covers such a cell when it has not been declared there: the row stays, with an empty value, so the gap is visible.

2.6 Which rows exist

For each indicator, the required rows are:

(the qualifier combinations declared in CL_INDICATOR.qualifiers) × (the cuts in TAB_PLAN that cover its theme and unit) × (the categories of those cuts) − (anything listed in excluded_breakdowns)

Nothing extra, nothing missing. A cell with no observations is a row with OBS_STATUS=O, not an absent row. This is what makes a file checkable: the validator can compute the set of rows that should exist and compare it with the rows that do.

2.7 Example rows

Table 6 shows the compositions of Table 3 as they are written in a data file. Only the columns that vary are shown.

In every row DATAFLOW=AFW360_HH, REF_AREA=SEN and TIME_PERIOD=2021. SEX and AGE are _T (total), or _Z for an indicator whose stat_unit is not IND (Section 2.2). COMP_BREAKDOWN_2…5 are _T, and MEASURE_QUAL_4…5 are _Z (not applicable).

Qualifiers fill the slots in ascending slot_order (Section 2.4): welfare concept 10, poverty line 20, PPP 30, COICOP 40, fiscal instrument 50. That is why the COICOP code lands in slot 3 on the “food share among the poor” row but in slot 1 on the “food share, poorest quintile” row.

3 Breakdowns

Read this before adding a new way of splitting the population.

A breakdown variable classifies units: sex of household head, consumption quintile, sector of employment, poverty status. It is one row in CL_BRK_VAR. Its categories are rows in CL_COMP_BREAKDOWN, and each category code begins with its variable code.

Adding one changes no structure. It takes a row in CL_BRK_VAR, a row per category in CL_COMP_BREAKDOWN, and a line in TAB_PLAN.

3.1 Initial breakdown variables

Table 7 lists the breakdown variables needed to reproduce the current tables and the first fiscal-incidence work.

slot_order values are spaced by 10 so that new variables can go in between, as DEC_MKT (15) and EMP_STATUS (55) already do.

DEC_MKT is registered for fiscal-incidence work, where households are ranked by market income; QUINT ranks them by consumption per capita. Two different rankings are two different variables, and each states its basis in definition_en.

3.2 Every breakdown variable carries a universe

CL_BRK_VAR.universe names the population that the categories partition. This is what makes POP_SH work as a single indicator: the share is the category’s N_POP divided by the universe’s N_POP, so “share of employed in agriculture” and “share of households with two enterprises” are the same indicator with different breakdowns.

3.3 Worked example: adding sector of employment

  1. Decide whose characteristic it is. “Sector of an individual’s main job” (EMP_SECTOR, describes IND) and “sector of the household head’s main job” (HHH_SECTOR, describes HHH) are two different variables. The first can break down only individual-level indicators; the second can break down household indicators such as the poverty rate.
  2. Register it in CL_BRK_VAR: describes = IND, applies_to_units = IND, universe = employed persons aged 15–64, classification = ISIC Rev.4, partition = Y, slot_order = 60.
  3. Register the categories in CL_COMP_BREAKDOWN: EMP_SECTOR_AGR for ISIC section A, EMP_SECTOR_IND for B–F and EMP_SECTOR_SER for G–U.
  4. Add a cut to TAB_PLAN.
  5. Produce the rows. When the cut is crossed with individual sex, the rows for women also carry SEX=F. When it is crossed with quintile, QUINT has the lower slot_order, so it takes slot 1 and EMP_SECTOR takes slot 2.

4 Qualifiers

Read this before adding a poverty line, a PPP round, a welfare concept or any other variant of an existing measure.

A qualifier variable changes what is measured for the same units. It is one row in CL_QUAL_VAR, and its categories are rows in CL_QUALIFIER. Adding one is a codelist change, not a structural one (Section 7.3). Table 8 lists the initial set.

4.1 Poverty lines

$2.15, $3.65 and $6.85 are the international, lower-middle-income and upper-middle-income lines at 2017 PPP; $3.00, $4.20 and $8.30 are their 2021 PPP replacements. POVLINE_NPL means “the national line of this survey”, whose value differs by country and round.

4.2 PPP beyond poverty

The PPP qualifier also marks values expressed in PPP dollars, such as mean consumption per capita per day in 2021 PPP dollars. Values in local currency carry no PPP code (_Z); their currency comes from CL_AREA.

5 Metadata files

This section is the reference for every CSV under metadata/ and content/: what each file holds and which columns must be filled. Most of them are codelists (CL_*). A codelist is the list of valid codes for one column of the data file, with the meaning of each code. The rest are registries (surveys, boundaries, figures) and the plan of which cuts to produce.

Rules for every CSV under metadata/ and content/:

  • UTF-8, comma-separated, one header row. Readers must open with utf-8-sig, because Excel’s “CSV UTF-8” writes a byte-order mark.
  • Multi-valued fields are space-separated.
  • No literal newlines inside a cell. Anything that needs paragraphs goes in a Markdown file (Section 9).
  • Column status: R required, C required when relevant, O optional.
  • Every codelist has these columns, plus the extra ones listed in its own subsection: code, name_en, definition_en, status (DRAFT, ACTIVE, DEPRECATED), version_added, replaced_by (C), notes (O).

5.1 Code rules

  • Uppercase ASCII letters, digits and _; start with a letter; at most 32 characters, the Stata variable-name limit. P-codes are used as issued and already comply.
  • _T and _Z are reserved sentinels and never appear as codes.
  • A code never changes meaning, and is never reused or deleted. A changed definition means a new code, with the old one DEPRECATED and replaced_by filled. Rewording a label is free.
  • Breakdown and qualifier categories are <var_code>_<category>. The whole code must still fit in 32 characters, so keep var_code short.
  • Indicator codes are <THEME>_<SUBJECT>[_<DETAIL>] and contain no poverty line, PPP round, welfare concept, COICOP division, unit or breakdown, because all of those are dimensions. Use POV_HC, never POV_HC_PL420.
  • In Stata, name the variable holding an indicator after its code in lower case, so no lookup table is needed.

5.2 CL_INDICATOR.csv: the indicator dictionary

Beyond the common columns, the dictionary has the columns in Table 10.

display_as fixes a defect the dashboard has today, where every value is formatted as a percentage. A share stored as 0.37 displays as 37.0%, and POV_NUM stored as 6520000 displays as 6.52 (millions).

checks vocabulary: RANGE_0_1, RANGE_NONNEG, AGG_SUM (totals sum over a partition), AGG_NPOP_MEAN (means aggregate as N_POP-weighted averages), SUM_TO_1_OVER:<QUAL_VAR> (for example COICOP), SUM_TO_1_OVER_BRK (categories of the breakdown sum to 1), EQUALS_NPOP_RATIO, MONOTONE_IN:POVLINE, NONE.

Why the population fields matter. HHH_SEX_F means “people living in female-headed households” for a person-level poverty rate, and “enterprises in female-headed households” for an enterprise indicator. Without stat_unit, universe_* and weight, person-weighted and household-weighted numbers end up on the same chart. statistic matters too: a budget share can be the mean of household shares (MEAN) or the share of aggregate spending (RATIO_TOTALS), and the two differ.

5.3 CL_BRK_VAR.csv

Beyond the common columns (code is the var_code), the file has the columns in Table 11.

5.4 CL_COMP_BREAKDOWN.csv

Extra columns: var_code (R), parent (O, a category of the same variable, for nested classifications), order (R, display order). definition_en is required wherever the boundary is not obvious, such as age cutoffs, ISIC groupings and quantile ranking rules.

5.5 CL_QUAL_VAR.csv and CL_QUALIFIER.csv

CL_QUAL_VAR extra columns: slot_order (R), requires (C, other qualifier variables that must appear with it, such as PPP for POVLINE), owner (R).

CL_QUALIFIER extra columns: var_code (R), value (C, the numeric parameter, such as 3.00 for POVLINE_PL300), basis (C, what that value is expressed in), valid_with (C, allowed categories of other qualifier variables), order (R).

5.6 CL_GEO_SCHEME.csv and CL_GEO.csv

Schemes are parallel, not nested. ADM1 regions, ADM2 départements, Senegal’s zones and Guinea-Bissau’s agro-ecological zones are four different ways of cutting a country, and each is stored as its own set of units. Even where one scheme happens to group the units of another, as Senegal’s zones group its regions, nothing is derived from that nesting, and no scheme is required to decompose into another.

CL_GEO_SCHEME has one row per country and scheme, keyed ref_area + code (Table 12).

CL_GEO has one row per spatial unit (Table 13).

The shapefiles in INPUT shp/ already carry these P-codes: SN01 is Dakar, SN03 is Fatick, and GW08 is Bissau (the current tables call it SAB). Maps join on codes, never on names.

5.7 CL_AREA.csv

Extra columns: iso2 (R, the P-code prefix), currency (R, ISO 4217), wb_region (R).

Currency matters more than it seems. “FCFA” is two different currencies: XOF (CFA franc BCEAO, used in WAEMU, including SEN and GNB) and XAF (CFA franc BEAC). Eight AFW economies use neither. Monetary values in LCU are therefore not comparable across countries; comparison needs a PPP-denominated indicator.

5.10 Manifest

AFW360_HH_<ISO3>_<YEAR>_manifest.csv has two columns, key and value. The keys are:

dataflow, dsd_version, metadata_version, ref_area, time_period, source_type (SURVEY, PROJECTION, ADMIN), survey_id (the base survey, also for a projection), precision (EXACT, or ROUNDED_2DP for legacy conversions), file_name, n_rows, producer, program, software, run_timestamp (ISO 8601), status (DRAFT, SUBMITTED, VALIDATED, PUBLISHED), notes.

TIME_PERIOD is the year the estimate refers to, which is not always a survey year. A microsimulated 2026 poverty rate has TIME_PERIOD=2026, source_type=PROJECTION and survey_id=SEN_EHCVM_2021, and every row has OBS_STATUS=E.

5.11 TAB_PLAN.csv: which cuts are produced

A cut is one way of splitting the population, such as by residence, by region or by quintile. A row that lists two breakdowns is a crossed cut, such as quintile by sex of household head. TAB_PLAN is what turns the dictionary into a list of required rows (Section 2.6).

There is one row per cut, with the columns in Table 16. They give the codes used, not yes/no flags.

The initial plan (Table 17) reproduces the current Excel tables. Every row has sex = _T, age = _T, themes = ALL and status = ACTIVE. The zone cut needs one row per country, because the two countries’ zone schemes differ.

6 What a producer delivers

This is the checklist for handing in a file. For each country and reference year, deliver:

  1. AFW360_HH_<ISO3>_<YEAR>.csv, UTF-8, with the 26 columns of Table 4 in that order.
  2. Every required row (Section 2.6), including cells with no observations.
  3. The manifest (Section 5.10).
  4. Any metadata changes the data need, in the same pull request (Section 10).

6.1 Estimation rules

  • Code the indicator variable as missing for units outside its universe, so they leave both the numerator and the denominator.
  • Estimate with the survey design declared (weights, strata, PSUs), and use subpopulation estimation for groups rather than dropping observations, so that standard errors stay correct.
  • Use the weight named in the dictionary (POP = household weight × household size, for person-level statistics computed on household data).
  • Publish every estimate. Do not blank, round away or drop a small cell; report its N_OBS.
  • Write values unrounded, in base units.

6.2 A note on legacy conversions

Files that the converter produces from the current Excel inherit values already rounded to two decimals, and they carry no sample sizes. Such a file sets precision = ROUNDED_2DP in its manifest. The validator then relaxes its aggregation tolerances and does not demand STD_ERR, CI_* or N_OBS. This exemption applies only to converted legacy files, never to new production.

6.3 How the dashboard shows reliability

Since nothing is suppressed, the dashboard carries the burden of honesty:

  • Every value is shown with its N_OBS, available on hover, in a details panel or in the downloaded table.
  • Charts show the confidence interval where one exists.
  • A cell resting on few records is visually de-emphasized rather than hidden, and OBS_STATUS=O renders as “no observations”, never as zero.

7 How to extend

Start here whenever you want to add something. Find the row in Table 18, edit the files it names, and bump the metadata version as shown (Section 10). Only one row changes the structure of the data file, and only the data team makes that change.

7.1 Add an indicator

  1. Search CL_INDICATOR for the same concept. If it exists, reuse it. Before creating a code, check whether the difference is a qualifier: a different poverty line, PPP round, welfare concept or COICOP division is never a new indicator. Neither is a population share; that is POP_SH with a breakdown.
  2. If a near-duplicate exists, fill related and related_note on both rows.
  3. Standardize the variables it needs in the harmonized microdata, so that the indicator is a plain aggregate of them (Section 1.4). Record them in source_questionnaire and source_vars, and the program that computes the indicator in program.
  4. Fill every R column and the C columns that apply, including qualifiers and checks.
  5. Produce it for every applicable cut.
  6. Open a pull request (Section 10).

7.2 Add a breakdown variable

Follow Section 3.3: decide describes and applies_to_units, write the universe, reuse an international classification if one exists, set slot_order, register the categories, and add the cuts. Expect small N_OBS in fine groups, and publish them anyway with their sample sizes.

7.3 Add a qualifier variable

  1. Confirm it is a qualifier: the population behind each category is the same one (Section 1.1).
  2. Register it with a slot_order and, if it depends on another qualifier, requires.
  3. Register its categories, with value, basis and valid_with where they apply.
  4. List it in the qualifiers field of every indicator that takes it, naming the allowed categories.

7.4 Add a country

Follow the order in Section 1.4: metadata first, data last.

  1. CL_AREA: add the country, with its ISO2 code (the P-code prefix) and its currency.
  2. CL_GEO_SCHEME: register every spatial scheme the country will publish, with the local name of each level.
  3. CL_GEO: register the units of each scheme, using the P-codes of the boundary file you will map with.
  4. Indicators: check each indicator in CL_INDICATOR against the country’s survey, and reuse the code wherever the definition holds. Where it does not, register a new code linked to the old one through related and related_note (Section 7.1). Never stretch an existing definition to fit.
  5. Breakdowns and qualifiers: map the survey’s own variable values to the shared codes, in the producer’s program. A country-specific category becomes a child of a shared code (a secondary-city stratum is parent = U), never an unrelated new code.
  6. SURVEYS: add each survey round, with its design, welfare aggregate and national poverty line.
  7. Boundaries: add the ADM0 and ADM1 boundary file and its GEO_SOURCES row (Section 8.4).
  8. TAB_PLAN: add rows only where the country’s cuts differ from the shared ALL rows, for example for its own zone scheme.
  9. Data: produce the data file and manifest for each reference year (Section 6), run the validator, and open one pull request with the metadata and the data together (Section 10).

Every other code comes from the shared codelists.

8 Boundaries and figures

Every non-tabular asset follows the same pattern: a stable ID, a row in a registry carrying provenance, license and checksum, a path fixed by convention, and references by ID, never by path. Assets are never edited by hand; a wrong unit name, for example, is corrected in CL_GEO, not in the boundary file.

8.1 Maps exist for countries and ADM1 only

has_geometry = Y is set for ADM0 and ADM1. Every other scheme, including ADM2, zones and agro-ecological zones, is published as tables with no map, no geometry file and no missing-geometry error. Neither Senegal’s zones nor Guinea-Bissau’s agro-ecological zones therefore need polygons.

8.2 Storage

Boundaries are stored as GeoPackage (.gpkg) files, one per country per boundary vintage, with one layer per level:

geo/boundaries/SEN_CODAB_v02.gpkg     layers: adm0, adm1

Why not shapefiles: a shapefile is 5–6 files that must travel together. Its DBF field names are cut at 10 characters (the current files show cod_versio and adm1_ref_n), its text fields stop at 254 characters, its encoding is declared in a side-car .cpg, and its .prj carries no authority code (the current files say GCS_WGS_1984 with no EPSG number). A GeoPackage is one SQLite file with UTF-8 text, long field names, several layers and an SRS with its authority code, and geopandas, QGIS, ArcGIS and R all read it.

Rules:

  • Required layer fields: geo_code (matching CL_GEO.code), ref_area, scheme. A name column may be kept for convenience, but CL_GEO is authoritative, and disagreement is a warning, not an error.
  • CRS: EPSG:4326 in storage. Reproject only for display or area computation.
  • Hygiene: valid geometries, one feature per code, units covering the country exactly once.
  • Vintages are explicit. valid_from and valid_to in CL_GEO describe the boundary release a code belongs to, not the period the data cover. SEN’s COD-AB v02 dates from 2024 while the data are for 2021, and that is not an error.
  • Derived layers are generated, never hand-edited. Simplified display copies live in geo/derived/ and may be rebuilt at any time; the simplification tolerance is kept in the build script.
  • Size: keep files in git while they are small. Beyond a few MB, use Git LFS or an external store, with the URL and checksum in the registry.

GEO_SOURCES.csv columns: source_id, ref_area, provider, version, valid_on, url, download_date, licence, attribution (the credit line the map must show), crs, file, layers, sha256, status, version_added, notes.

8.3 Figures

Figures live at assets/figures/<ISO3>/<figure_id>.<ext> and are registered in FIGURES.csv, with columns figure_id, ref_area, time_period, theme, title_en, caption_en, alt_text_en (required: what a screen reader announces), indicators, source, producer, program, licence, file, sha256, status, version_added, notes.

Prefer generating figures from the data; an image is a last resort. Use SVG or PDF for charts, and PNG at twice display size for anything raster. The dashboard asks for a figure_id, not a file name.

8.4 Extending

9 Dashboard text

All prose the dashboard shows lives in one place and is written by hand, in English.

content/TEXT.csv                one row per slot
content/text/<ISO3>/<slot>.md   long-form bodies

9.1 TEXT.csv

A country row overrides an ALL row for the same slot. This keeps shared methodology in one place instead of copied per country; today About.txt and About_SEN.txt are byte-identical copies.

Markdown in body and in the files is limited to paragraphs, emphasis, links, lists and footnotes. No raw HTML.

9.2 Live numbers in prose

Numbers typed into prose go stale, and nothing checks them; the current key messages are typed into index.qmd by hand. Instead, reference the data inline, as in Listing 2.

  • The country and year come from the TEXT.csv row, and every breakdown defaults to the national total, so a plain {INDICATOR:QUALIFIER} is usually enough.
  • Anything else is added after @ as DIMENSION=CODE, separated by commas.
  • The dashboard formats each number with its indicator’s display_as and decimals (37.0% for a share, 6.52 for a count shown in millions), so prose and tables cannot disagree. Write only the words around the number.
  • The validator resolves every reference to exactly one observation, and fails if it finds none or several.

9.3 What this replaces

TEXT.csv replaces About_<ISO3>.txt, Messages_<ISO3>.txt and every string hardcoded in index.qmd. Figure captions stay with their images in FIGURES.csv.

9.4 Extending

Add or edit a row in TEXT.csv, and add a .md file if the text is long. The same pull request rules apply as for codelists.

10 Change control

This section says how a change gets into the database.

  • metadata/ and content/ live in git. Producers extend them on a branch and open a pull request, which the data team reviews.
  • Rows are append-only: no deletions, and no changing an existing code or its meaning. Deprecate instead.
  • Every merged change bumps metadata/VERSION (MAJOR.MINOR.PATCH, as shown in Table 18) and adds a line to metadata/CHANGELOG.md.
  • Every data file’s manifest records the metadata_version it was produced against.
  • The validator must pass before a pull request is merged or a file is published.
  • Editing a CSV in Excel is fine if you save as “CSV UTF-8” and check that codes have not been turned into numbers or dates. The byte-order mark that Excel writes is expected and is stripped on read.

Structural changes, meaning adding, removing or reordering a column, are made by the data team only. They need a new DSD_AFW360_HH.csv and a major version, and the converter must backfill existing files with _T or _Z. DSD_AFW360_HH.csv itself has the columns position, id, role (constant, breakdown, reference, qualifier, measure, attribute, as in Table 4), codelist, required, sentinel and description, and the data-file header must match it exactly.

11 Validation checks (to be implemented in Python)

This is the specification for the validator. Each check is phrased so that it can be implemented directly, and together they enforce every “must” in Sections 2 to 9.

Structure

  • The header matches the DSD exactly: same names, same order (after stripping a BOM).
  • No dimension or qualifier cell is empty.
  • The key, meaning all dimension and qualifier columns together, is unique.

Codes

  • Every code exists in its codelist. Newly produced rows use ACTIVE codes; existing rows are valid against any code that is not DRAFT, with valid_from / valid_to respected for geography.
  • GEO belongs to REF_AREA, and its scheme is registered for that country.
  • Breakdown slots are filled from the left in canonical order, with no variable twice, and unused slots are _T.
  • Qualifier slots follow the same rules, and unused slots are _Z.
  • SEX and AGE are _Z when the indicator’s stat_unit is not IND, and _T or a code otherwise.
  • Breakdown variables are compatible with the indicator’s stat_unit.
  • Every qualifier used is declared by the indicator, or required by a breakdown in the same row.
  • valid_with pairings hold, for example POVLINE_PL420 only with PPP_2021.

Coverage

  • The rows equal the set defined in Section 2.6: nothing missing, nothing extra.
  • Nothing listed in excluded_breakdowns appears.
  • A SURVEYS row and a manifest exist, and the manifest matches the file.

Values

  • OBS_VALUE is numeric and within valid_min / valid_max.
  • OBS_VALUE is empty exactly when OBS_STATUS is O or M.
  • STD_ERR ≥ 0 and CI_LOWER ≤ OBS_VALUE ≤ CI_UPPER.
  • N_OBS is a non-negative integer and N_POP is non-negative. Both are present except in legacy files (Section 6.2).
  • N_OBS = 0 implies OBS_STATUS = O.

Verification rules from checks

  • AGG_SUM: children sum to the parent over a partition.
  • AGG_NPOP_MEAN: the N_POP-weighted average of the children equals the parent.
  • SUM_TO_1_OVER:<QUAL_VAR> and SUM_TO_1_OVER_BRK: the categories sum to 1.
  • EQUALS_NPOP_RATIO: the value equals the child’s N_POP over the universe’s.
  • MONOTONE_IN:POVLINE: the value does not fall as the line rises.
  • RANGE_0_1, RANGE_NONNEG.
  • The parent of a row is the same row with one breakdown set to _T. If that breakdown required a qualifier (POOR requires POVLINE), the qualifier is cleared to _Z in the parent, unless the indicator itself declares it.
  • Children’s N_POP sums to the parent’s for any partition = Y breakdown.
  • Tolerances are relaxed for manifests with precision = ROUNDED_2DP.

Assets

  • Every geo_code in a geometry layer exists in CL_GEO with the same ref_area and scheme.
  • Every CL_GEO code whose scheme has has_geometry = Y has a geometry; schemes with N are skipped.
  • Geometries are valid, unique per code, and in EPSG:4326.
  • Every registry row points at a file that exists, with a matching sha256.

Text

  • Every {…} reference resolves to exactly one observation.
  • Exactly one of body and file is filled, and referenced files exist.
  • Every slot the dashboard requests exists for the country and year, or inherits from ALL.

Metadata files

  • Codes are unique and follow Section 5.1.
  • Every R column is filled.
  • Every var_code, parent, replaced_by, source_id, scheme and nests_in reference resolves.
  • slot_order values should be unique within CL_BRK_VAR and within CL_QUAL_VAR. A tie is a warning, not an error, and is broken alphabetically.

12.2 Open decisions

  1. Age cutoff for household heads. The current Youth_HH / Older_HH boundary is undocumented; confirm it before publishing any HHH_AGE_* code.
  2. Quintile definition. National or within-area ranking, person- or household-weighted. The answer goes in CL_BRK_VAR.definition_en.
  3. Governance. Who owns metadata/ and reviews pull requests.
  4. GNB survey metadata. About_GNB.txt contains only a placeholder, so the survey round and its TIME_PERIOD are unknown.
  5. Where large binaries live. Git, Git LFS, or an external store referenced from GEO_SOURCES.csv.
  6. Boundary vintage policy. Who decides when to adopt a new COD-AB release, given that P-codes can change and older data must still resolve.
  7. Where variable-level metadata lives. Section 1.4 asks for documentation of every harmonized microdata variable behind an indicator. CL_INDICATOR names those variables but has nowhere to describe them. A variable dictionary per survey, kept with the producer programs or under metadata/, is the obvious candidate.
  8. A country that cannot produce an indicator. Section 2.6 requires every indicator for every country, and there is no way yet to record that a survey does not support an indicator at all.
  9. The Departement sheet. Its 60 indicators shared with ADM 1 would produce rows with the same key but mostly different values (Annex 2). The converter must either take only its 2017-PPP poverty rows or skip the sheet.
  10. Reference syntax for live numbers. Section 9.2 is a sketch. It does not yet say how a reference names several qualifiers, or confirm that PL420 is shorthand for POVLINE_PL420.
