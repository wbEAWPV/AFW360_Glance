Appendix B. The data transition

How the legacy Excel, shapefile and text inputs became data in the AFW360 standard

Published

September 29, 2026

In September 2026 the dashboard’s inputs were converted, without changing a single number, into the files defined by the data standard. This page summarises what was done, which part was done by code and which by hand, and where each piece lives.

In one paragraph

The dashboard used to read two Excel workbooks in which every row is identified by a free-text label and every column by a spelled-out region name. The transition kept those files untouched in data_raw/, wrote down by hand how each label and column maps to a coded indicator, breakdown and area, and used R code to turn that mapping into a documented, machine-checkable dataset: one long table per country and year, plus codelists, boundaries, text and figures. The output reproduces every value in the workbooks, and it is marked DRAFT until the team confirms it.

What was done by hand

These are the judgement calls. Everything else is derived from them by code.

  • The mapping of the workbooks. pipeline/bootstrap/seeds/ holds seven small tables written during the transition:
    • label_triage.csv: each of the 179 workbook labels, what it measures, and whether to keep, skip, or treat as a duplicate or derivable series;
    • codes.csv: the codes and hierarchies of every codelist (breakdowns, qualifiers, units…);
    • geo_codes.csv: the 35 regions and zones, with the workbook column each one came from;
    • legacy_national_columns.csv: what each column of the National sheet means (urban/rural, sex of head, quintile…);
    • tab_plan.csv: which breakdowns are published for which geography;
    • legacy_overrides.csv: the 12 cells or columns withheld or flagged as wrong;
    • csv_headers.csv: the columns of every metadata file.
  • The definitions. pipeline/bootstrap/text/ holds the names, definitions, universes and notes of every indicator, breakdown, area, survey and figure (about 250 entries).
  • The standard itself. data-standard.qmd was revised to v0.4 to close 27 gaps found while writing the mapping, and to v0.5 after the acceptance (see below).
  • The decisions. The team settled the questions the data could not answer (see below).

What was done by code

All code is in R, under pipeline/. Every script runs from the repository root with --root ., and running it twice gives identical files.

Step Script Reads Writes
1. Freeze the inputs (one-off move) the original input folders data_raw/, with CHECKSUMS.sha256 proving no byte changed
2. Build the metadata pipeline/bootstrap/build_*.R the seeds and texts above metadata/codelists/, plans/, surveys/
3. Build the boundaries pipeline/build_geo.R data_raw/shp/ geo/boundaries/*.gpkg, metadata/registries/GEO_SOURCES.csv
4. Build text and figures pipeline/build_content.R data_raw/text/, data_raw/figures/, index.qmd messages content/, assets/, FIGURES.csv
5. Convert the tables pipeline/convert_legacy.R data_raw/tables/, metadata/plans/, metadata/registries/SOURCES.csv data/AFW360_HH_<ISO3>_2021_SURVEY.csv and its manifest
6. Check the result pipeline/validate.R everything above a list of errors and warnings
7. Check the conversion pipeline/reconcile.R the workbooks and data/, independently of step 5 a cell-by-cell report
8. Generate the standard’s tables pipeline/build_docs.R metadata/, content/ .docs/generated/*.md, included by the standard

Shared functions are in pipeline/R/, and unit tests in pipeline/tests/.

The bootstrap scripts (step 2) are now frozen. From metadata version 0.1.0 onward the metadata CSV files themselves are the source of truth, and they are edited directly. The seeds and bootstrap scripts are kept as the record of how the first version was built. Later structural changes are made by one-off scripts under pipeline/migrations/<version>/; the first, 0.2.0/migrate.R, took the metadata from 0.1.0 to 0.2.0 (below).

Main decisions

  • Inputs are never edited. Every fix goes into the mapping or the code, so the original workbooks remain the audit trail.
  • SEN Departement sheet skipped. It is an older version whose poverty totals disagree with ADM 1.
  • Known-bad values withheld, not corrected. The GNB Capital column (a copy of a zone) and 7 GNB cultivated-area outliers (up to 148 million ha) are left out and registered in LEGACY_OVERRIDES.csv.
  • Empty cells kept as empty. They are recorded as “no value available” (OBS_STATUS = O) with a comment, never filled.
  • Three kinds of population share. A share of individuals, of households and of household enterprises get separate codes, because each needs its own weight.
  • GNB survey dated 2021. EHCVM 2021/22 is recorded as 2021.
  • Key messages taken from the dashboard. The version hard-coded in index.qmd was preferred over Messages_<ISO3>.txt.
  • 19 ambiguous indicators coded as recommended. Examples: non-food share derived from the food share; three electricity indicators kept but flagged; household-head age groups kept as draft codes. All 19 were confirmed by the team and remain DRAFT.

Results

  • Senegal: 3,003 values (91 series × 33 population groups).
  • Guinea-Bissau: 2,268 values; 98 withheld as known errors; 39 empty in the source.
  • Coverage: every one of the 5,723 source cells is accounted for exactly once: converted, derived, duplicated, withheld or skipped.
  • Dictionary: 62 indicators, 13 breakdown variables (60 groups), 6 qualifiers (42 values), 35 geographic units in 6 schemes.
  • Checks: the validator finds no errors; the independent reconciliation matches every value.
  • Poverty headcounts reproduced exactly: SEN 3.13M / 6.52M and GNB 0.70M / 1.09M poor at $3.00 / $4.20 (2021 PPP).

What is still open

  • The dashboard still reads data_raw/. Pointing it at data/, metadata/, geo/ and content/ is the next step. (Done in the SDMX transition, below.)
  • Everything is DRAFT. Codes become ACTIVE only once the team confirms them.
  • The workbooks carry no sample sizes, population counts or standard errors. Producer files with those columns should replace them.
  • Some questions in the standard remain open: quintile definition, who owns metadata/, and the policy on boundary versions. How to record an indicator a country cannot produce was settled in v0.5 (a country row in SERIES_PLAN.csv).

After acceptance: standard v0.5 and metadata 0.2.0

On 2026-09-28 the standard was reviewed against the SDMX information model and revised to v0.5, with the metadata migrated to 0.2.0 and the data files regenerated. The review found the model sound and closed three kinds of gap: a data row could not be read from its key and the DSD alone, unit and provenance metadata sat at the file level rather than the row, and the population count on share rows was defined twice. In short:

  • Every data row now carries SERIES_ID, UNIT_MEASURE, PRECISION and SOURCE_ID, and the key gains an ESTIMATION dimension (SURVEY or MODEL), so a nowcast and a survey estimate for the same year can coexist. Files are named AFW360_HH_<ISO3>_<YEAR>_<ESTIMATION>.csv.
  • Verification rules and the indicator–qualifier relations moved out of codelist cells into metadata/rules/RULES.csv, metadata/structure/INDICATOR_QUALIFIERS.csv and QUALIFIER_PAIRS.csv; program runs are registered in metadata/registries/SOURCES.csv.
  • OBS_STATUS gains a rule-based low-reliability code and a definition-differs code; SERIES_PLAN.csv gains display names and per-country status.
  • Every table in the standard that lists a metadata file is generated from it and checked for staleness.

The decisions are recorded as D12 to D26 in the standard’s “Changes since v0.4” table. The values in data/ are unchanged: projecting the new files onto the old 26 columns reproduces the accepted files exactly, and the reconciliation still matches every cell.

How the work was run

The transition was carried out by AI agents in 17 work packages, each checked by an independent verifier, with the team deciding at three gates (hard cases, the standard, final acceptance on 2026-09-23). The detailed plan, the per-package instructions and the verification reports were removed once the work was accepted. They remain in the git history at commit af378e9, under .docs/transition/.

SDMX transition (standard v0.6, metadata 0.3.0)

On 2026-09-29 the files themselves were made SDMX 3.1 conformant, with the standard revised to v0.6 and the metadata migrated to 0.3.0 by pipeline/migrations/0.3.0/migrate.R. v0.5 already followed the SDMX information model in spirit; v0.6 makes the published files readable by SDMX tools while keeping CSV as the working format and the CSVs under metadata/, content/ and data/ as the source of truth. The same step switched the dashboard from data_raw/ to the harmonised files. In short:

  • Data. The two data files are SDMX-CSV 2.1 data messages: three fixed leading columns, one column per component of the data structure, 37 columns with a 19-column key, a FREQ dimension first, ACTION R on every row, and NaN where a value is intentionally missing.
  • Structures. pipeline/build_sdmx.R generates one SDMX-ML 3.1 structure message, sdmx/structures/AFW360_structures.xml, with 32 maintainables: the agency scheme, 22 codelists, a concept scheme of 82 concepts, the data structure and dataflow, the metadata structure and metadataflow, the data and metadata provider schemes and the two provision agreements. Agency WB.AFW360 is declared as a sub-agency of the World Bank’s WB. The file is validated against the vendored SDMX-ML 3.1.0 schemas before it is written.
  • Reference metadata. Surveys, sources, dashboard text and figures are published as four SDMX-CSV 2.1 metadata messages under sdmx/metadata/, generated from the registry CSVs.
  • Round trip. pipeline/import_sdmx.R turns a structure message (SDMX-ML 3.0 or 3.1) back into the metadata CSVs. Importing the generated message and rebuilding gives the same file byte for byte.
  • Checks. The validator gains six SDMX.* checks (staleness, schema, references, identity, data-file header, skipped). tools/verify/ checks the same files independently with pysdmx and lxml.
  • Dashboard. afw360/loader.py is the single data-access layer; the Senegal and Guinea-Bissau sections and the About page read data/, metadata/, content/, geo/ and assets/ through it. Guinea-Bissau now shows its own data, and every cell follows its indicator’s display rule.
  • Fusion Metadata Registry. FMR 12.4.2 was installed locally under tools/fmr/runtime/ (Tomcat 10.1, MySQL 8.0, no Docker, no administrator rights). It rejects SDMX-ML 3.1, so build_sdmx.R --sdmx-ml-version 3.0 writes a 3.0 profile without the metadata structure, metadataflow and metadata agreement. FMR loads that profile once the WB agency is registered, validates both SDMX-CSV 2.1 data files unchanged, and exports SDMX-ML 3.0, which the importer reads back with an empty diff. The workflow is in the FMR guide.

The decisions are recorded as D27 to D46 in the standard’s “Changes since v0.5” table and in metadata/CHANGELOG.md; the SDMX conformance page gives the evidence for each requirement. The main ones: target the SDMX 3.1 family (SDMX-CSV 2.1 for data and reference metadata, SDMX-ML 3.1 for structures, no SDMX-JSON); keep the pipeline in R, with Python only in the dashboard loader and the verification tool; align project codes to global SDMX, SDG and World Bank codelists where one exists; nine measures; registries become codelists plus metadatasets; SERIES_ID stays an uncoded attribute, because series ids contain dots.

The results: every value in data/ is unchanged (the reconciliation matches all 6871 cells, and projecting the new files onto the v0.5 columns reproduces them); the validator reports no errors; the test suite holds 1503 expectations; the SDMX files and the generated tables of the standard are current; the independent reader reports no failures.

What remains open: every code is still DRAFT; FMR cannot read the 3.1 message or the metadata structure, so the reference metadata files are checked only by the build, the validator and tools/verify; the page is not yet laid out as a Quarto dashboard.

The work was run as 30 work packages and three gates, all on 2026-09-29, on branch standard/v0.6-sdmx. An orchestrating agent wrote a brief for each package; Opus agents implemented them and fresh Sonnet agents verified each one against its own checklist before it was committed. The data lead decided at Gate 1 (the design, decisions D38 to D46), Gate 2 (install FMR now rather than defer) and Gate 3 (final acceptance and merge). The plan, the progress log with every commit hash and the surfaced points are in .docs/sdmx-transition/.
