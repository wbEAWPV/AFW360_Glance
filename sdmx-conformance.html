SDMX conformance

Checklist with evidence · standard v0.6 · metadata 0.3.0

Published

September 29, 2026

This page is the evidence that the AFW 360 files conform to the SDMX 3.1 family chosen in the standard (D27): SDMX-ML 3.1.0 for the structure message, SDMX-CSV 2.1.0 for data and reference metadata. Each row names a requirement, the command that checks it, and the result observed on 2026-09-29 on branch standard/v0.6-sdmx.

Commands run from the repository root in Git Bash. V is tools/verify/.venv/Scripts/python (Python 3.11, pysdmx[data,xml]==1.20.0, created by tools/verify/make_venv.sh or make_venv.ps1) and X is sdmx/structures/AFW360_structures.xml. The Python tools are for verification only and are never part of the R pipeline (D30). Rows 1 to 12 and 14 were rerun for this page; row 13 comes from the FMR run of the same day, whose reports are kept under tmp/fmr/ (gitignored).

Checklist

The whole validator run of row 6 exits 0 with these findings and no ERROR: 42 CODES.DRAFT and 42 META.TBD warnings, 27 RULE.AGG_SKIPPED warnings, 4 TEXT.TBD warnings, 6 RULE.CLOSURE_PARTIAL and 2 VALUE.N notes. None is an SDMX finding.

Notes on the evidence

Vendored schemas (row 1). pipeline/xsd/sdmx-ml-3.1/ holds the 30 files of schemas/ at tag v3.1.0 of sdmx-twg/sdmx-ml, entry SDMXMessage.xsd. The repository has no LICENSE, LICENCE or COPYING file at that tag and its README states no licence terms, so the folder’s README.md records the absence instead of quoting a licence. xml2::xml_validate() in build_sdmx.R and the validator’s SDMX.XSD check use the same schemas. pysdmx’s own read_sdmx(validate=True) validates against its bundled schemas, not these; xsd_validate.py covers the vendored ones.

pysdmx 1.20.0 limits (rows 8 and 12). pysdmx cannot read com:AnnotationValue, which the XSD allows and every codelist here uses; verify_sdmx.py validates the original bytes and hands pysdmx a copy without annotation values. It has no SDMX-CSV metadata reader (Format.REFMETA_SDMX_CSV_2_1_0 exists but no reader uses it), so the metadata messages get a header check: fixed columns, MDSTRUCTURE = metadataflow, TARGET_IDS naming an artefact of the message, and dotted headers whose last segment is an MSD attribute id. It does not check the parent prefix, MDSTRUCTURE_ID, TARGET_TYPES or the uniqueness of METADATASET_ID; the byte comparison of SDMX.STALE covers those. check_urns.py registers a maintainable without a version attribute (the organisation schemes) under version 1.0.

Legacy regression (rows 7 and 11). pipeline/reconcile.R matches every cell of the data files against the legacy workbooks (6871 cells OK, 98 GNB cells withheld by LEGACY_OVERRIDES.csv). The projection test in pipeline/tests/testthat/ maps each data file back onto the 31 columns of the previous layout and finds only the removed DATAFLOW column and NaN against empty on the 39 GNB O rows. Its comparator is unit-tested; the whole test has not been mutation-tested.

What the FMR round trip does not cover (rows 11 and 13). The MSD, the metadataflow and the metadata provision agreement are not in the 3.0 profile, so FMR neither loads nor exports them. import_sdmx.R does not write back the ARTEFACTS.csv columns status, version_added, notes, agency_id and source_file, edits to the derived codelists, AFW_METADATA_VERSION, the structure of the concept scheme, DSD, MSD, dataflow and agreements, non-English names, or sentinel names and their GLOBAL_CODE. The 3.0 profile keeps AnnotationValue, which FMR accepted; it has not been checked against the 3.0 XSDs.

FMR’s clean report. An FMR validation report says "Errors":false when the file is clean; the word “error” appears in a clean report, so the field, not a text search, is the test.

Not claimed

  • No DataConstraint and no VTL: required coverage and arithmetic rules are checked by the project validator (D45).
  • SERIES_ID is an uncoded String attribute checked against SERIES_PLAN.csv, not a codelist (D43, IDType forbids the dot in series ids).
  • WB:AGENCIES is a local placeholder declaring AFW360; nothing is registered in the Global Registry (D31).
  • Sender id WB_AFW360: message sender ids are IDType and cannot contain the dot of WB.AFW360.
  • Byte-identical regeneration of the boundaries: pipeline/build_geo.R writes GeoPackages that are not byte-deterministic, so a rebuild changes geo/boundaries/*.gpkg and the two sha256 fields of metadata/registries/GEO_SOURCES.csv, and the regenerated tree fails the byte-identity test of test-migrate-0.3.0.R (WP11). The committed GeoPackages and hashes are the reference; a deterministic writer needs a metadata patch version and a migration and is left for a later release.
