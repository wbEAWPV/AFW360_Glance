Appendix B.1. AFW 360 transition plan

From the legacy Excel, shapefile and text inputs to the AFW360 data standard · revision 2

Published

September 21, 2026

This plan converts the dashboard’s current inputs (two Excel workbooks, 22 shapefile layers, a handful of text files and one image) into the files defined by the data standard:

  • codelists and plans under metadata/;
  • one long CSV per country and year under data/;
  • boundaries under geo/;
  • prose and images under content/ and assets/.

Every file is produced by R code under pipeline/, so the conversion can be read, rerun and checked. The dashboard keeps working throughout, and it switches to the new files only after this plan is complete.

The plan is carried out by agents working in parallel. An orchestrator running on Opus launches them and takes decisions to the user, and it never edits or runs anything itself. Implementers, verifiers, patch agents and integrators running on Sonnet do all the work. Each package is checked by a verifier that did not build it. The user decides at three gates, and nothing becomes ACTIVE without the user.

Revision 2 follows a review of the first plan; Section 9 lists what changed and why.

1 The document set

Cards are self-contained. A card carries the rules its package needs, taken from the standard, the contract and the decisions. An agent therefore reads two short files and a few filtered rows, not the whole document set. Machine-readable files win. Where prose and a contract/*.csv file disagree, the CSV is right, and the disagreement is reported.

2 Starting point

This is what the repository holds on 2026-09-21, on branch dev/eb. WP00 tags the starting commit as transition-base.

2.1 Inventory

There are 122 tracked legacy files. WP01 moves every one of them to data_raw/.

index.qmd refers to these inputs by path in 12 places: lines 188, 370, 371, 658, 665, 675, 694, 1115, 1122, 1132, 1151 and 1182. WP01 changes only those strings.

2.2 What shapes the transition

The full findings are in input-tables-findings.qmd.

  • Each sheet is a set of one-way breakdowns of the national population. Breakdowns are never crossed.
  • Rows are identified only by 97 free-text labels, which are byte-identical across sheets and countries. The poverty line, PPP round, unit and classification are all written inside the label.
  • Values are rounded to 2 decimals and stored as shares (0–1) or levels, with no unit field. An empty cell is ambiguous.
  • Regions and zones are identified by spelled names. Some names are cut at 32 characters, and GNB’s names carry accents. The COD-AB P-codes are already in the shapefiles (SN01–SN14, GW01–GW09); Bissau is GW08, which the tables call SAB.
  • Two SEN polygons, SN01 and SN13, are invalid as delivered.

3 End point

When the plan is complete, the repository holds the layout below. Everything in it is DRAFT until the user promotes it.

data_raw/                  the 122 legacy files, byte-frozen, with checksums
metadata/                  VERSION 0.1.0, CHANGELOG, structure/ (DSD, COLUMNS), codelists/, surveys/, plans/, registries/
data/                      AFW360_HH_SEN_2021.csv, AFW360_HH_GNB_2021.csv, and a manifest for each
geo/boundaries/            SEN_CODAB_v02.gpkg, GNB_CODAB_V01.gpkg (layers adm0, adm1)
content/                   TEXT.csv, text/SEN/about.md
assets/figures/SEN/        the fiscal-equity figure
pipeline/
  R/                       io, constants, codes, ctx, plan, geo, content, convert_tables, manifest, reconcile, validate_*
  bootstrap/               one-time generators of the metadata files, and their text seeds
  build_geo.R  build_content.R  convert_legacy.R  validate.R  reconcile.R
  tests/testthat/          unit tests
  acceptance/              one independent acceptance script per package, plus run_all.R

A hard-case flip at gate G0 changes some of these numbers. WP99 then updates expected_counts.csv, and every check reads its targets from that file.

What does not change. The dashboard still reads the legacy files, from data_raw/ after WP01. No value is recomputed from microdata: the transition restructures and documents what the workbooks contain, and withholds what is known to be wrong.

4 Decisions this plan rests on

The full record is in decisions.qmd.

  • D1 Tooling. The metadata bootstrap, converter and validator are written in R. The dashboard stays Python.
  • D2 Raw inputs. All legacy files move to data_raw/, byte-identical.
  • D3 Departement. The sheet is skipped entirely.
  • D4 Shares. Three codes: POP_SH, POP_HH_SH and POP_HE_SH.
  • D5 Defective cells. Their rows are absent, and each is registered.
  • D6 GNB survey. EHCVM 2021/22, TIME_PERIOD=2021.
  • D7 and D10 Hard cases. They are built with the recommended coding as DRAFT, and the user confirms or flips each at gate G0, before anything is built.
  • D8 Execution. Parallel agents only. The Opus orchestrator never executes; Sonnet agents do the work.
  • D9 Empty legacy cells. OBS_STATUS=O, with a LEGACY_EMPTY: comment.
  • D11 Metadata by code. Every metadata file is generated by a script under pipeline/bootstrap/ from the contract seeds and an authored text file. From version 0.1.0 onward the CSV files are the source of truth.
  • D12 Line endings. .gitattributes pins generated text to LF and marks data_raw/ as binary.

5 How the transition runs

5.1 Principles

  1. Small context.
    • An agent reads COMMON.md, its card, and a few filtered rows: about 10,000 to 25,000 tokens.
    • Its whole session stays under 100,000 tokens, and 150,000 is the hard limit.
    • An agent that runs long stops, and reports PARTIAL. A fresh agent then continues.
  2. Contract first. The packages of a wave build against the contract seeds, not against each other’s output. contract/check_contract.R proves that the seeds agree with each other and with the workbooks.
  3. Code, not typing.
    • Metadata files are generated by scripts from the seeds.
    • Agents write text (names, definitions) only where there is no source for it.
    • Every generator can rebuild into a temporary directory, so any file can be checked by regenerating it.
  4. Real inputs for the validator. The validator is written in wave 3 against the real, merged metadata, never against invented fixtures.
  5. Ownership. Every output path has exactly one owner in contract/output_ownership.csv. An agent that needs another path stops and reports.
  6. Independent verification. The verifier writes its own acceptance script from the card. The scripts are kept, and they are rerun after every merge.
  7. State in git. Branch names and commit subjects (WP05: verify v1 - VERDICT: PASS) record the state of the run. A new orchestrator session resumes from them.
  8. Nothing is pushed, and nothing reaches dev/eb before the user says so at G2.

5.2 Roles

5.3 Packages

Names derive from the table. The implementer branch is transition/wpNN-<slug>, verifier branches add -v<K>, and patch branches add -p<K>. The acceptance script is pipeline/acceptance/wpNN_<slug>.R. Reports are reports/WPNN-implementer.md, WPNN-implementer-p<K>.md and WPNN-verifier-v<K>.md.

5.4 Waves and gates

Why the waves fall where they do.

  • Wave 2 needs the scaffold’s writer functions (WP03), the inputs in data_raw/ (WP01) and a frozen contract (G1).
  • Wave 3 needs the real metadata. The validator is tested on it; the converter reads it; and the reconciliation tool is written at the same time as the converter, without seeing its code, so that it checks the converter independently.
  • The hard cases are asked first because every answer can be given from the evidence already in decisions.qmd. Asked first, a flip costs one edit of the seeds. Asked after the build, it would cost patches in up to three packages, and it would change counts that the acceptance scripts had already fixed.

5.5 Package life cycle

After every merge, the integrator reruns every acceptance script written so far, plus the unit tests. A failure is reported against the package that owns the broken file, and that package gets a patch agent. The integrator never fixes anything. It ends with one of three statuses: INTEGRATED; FINDINGS, when every failure has an owning package, so patch agents are sent without asking the user; or BLOCKED, when a branch cannot be merged or a failure has no owner, which goes to the user. A failed WP17 audit is handled like integrator findings: patches, a follow-up wave-3 integration, then the audit again as v2. Validator findings on the real data at wave 3 go first to the package that owns the check (FINDINGS mode): that agent decides, from its card’s rules, whether the check or the data is wrong.

5.6 Branches

dev/eb ──(WP00)──► transition/main ◄── integrator merges PASS branches, wave by wave
   │ tag: transition-base  │
                           ├── transition/wp05-geography          implementer
                           │     └── …-v1                           verifier: acceptance script and report
                           │           └── …-p1 ── …-v2             patch after a FAIL, then a fresh verifier
                           └── …

Every agent ends with git switch --detach, so that no worktree keeps a branch locked. If an agent dies before that step, a scout finds the stale worktree, and the rerun frees the branch with git -C <stale worktree> switch --detach, which deletes nothing. WP00 can be run again after a failed environment check: its card treats the second run as a retry. The final merge into dev/eb takes WP17’s PASS branch, which is transition/main plus the audit.

6 Verification

Verification happens at four levels.

  1. The contract is checked before it is used. check_contract.R runs in WP00, in the wave-1 integration, and after any flip. It checks:
    • code syntax and references;
    • the series-ID rule;
    • labels and columns, byte for byte against the workbooks;
    • that the plan’s row count equals the count of mapped workbook cells (3,003 and 2,366);
    • every EQUALS and ONE_MINUS assertion on the raw cells;
    • every recomputable number in expected_counts.csv.
  2. Every package is checked by an independent script from its card. The scripts are committed, and they rerun after each merge (pipeline/acceptance/run_all.R). They compare against the tag transition-base and against files, so they keep passing after the merge.
  3. The wave-3 integration runs the converter, the validator and the reconciliation on everything together.
  4. The final audit (WP17) checks every row of expected_counts.csv against the finished repository, and produces the tables shown at G2.

The validator’s aggregation, closure, monotonicity and range rules were tested against the raw workbooks when this plan was written. With the contract’s tolerances, the legacy data break none of them: 980 aggregation checks ran, and 112 were skipped for withheld or empty cells.

7 Risks and pitfalls

  • Context overrun. The first plan made every agent read about 110,000 tokens before starting. Cards are now self-contained; COMMON.md section 1 sets the reading and output rules; and a long session ends as PARTIAL instead of degrading.
  • Line endings. core.autocrlf=true would check generated CSVs out with CRLF in every new worktree. .gitattributes pins them to LF and marks data_raw/** as binary. WP01 restores the exact bytes after the move, and checks that look at bytes use git blobs.
  • Environment. Quarto needs QUARTO_R unset and QUARTO_PYTHON="C:/WBG/Python313/python.exe". WP00 proves the render before anything else runs.
  • Silent type changes. Read every CSV with all columns as character, write NA as an empty string, and never let a number print in scientific notation.
  • Encoding. Workbook headers carry accents, labels carry – and ≥, and one sheet is named ADM 1. Match them byte for byte; never retype them.
  • Geometry. Build with GEOS (sf_use_s2(FALSE)) and st_make_valid. A GeoPackage’s bytes change on every build, so it is compared by content.
  • Validator against real data. The first full validation can show errors that are the validator’s own. The wave-3 loop sends each finding to the check’s owner first, which decides where the fault lies.
  • Parallel collisions. A path owned twice, or a merge conflict outside the integrator’s own files, is a defect in the contract. The integrator aborts that merge and reports it.
  • Scope creep. Agents do not fix defects in the inputs. They register them.
  • Worktrees pile up. Each agent leaves a worktree behind. After G2, the user can remove them with git worktree list and git worktree remove <path>; every branch stays in the repository.

8 After the transition

These steps are out of scope for this plan:

  • Point the dashboard at data/, metadata/, geo/ and content/ through one loader per country (objective 3 in CLAUDE.md), and fix the display bugs listed there.
  • Promote confirmed codes from DRAFT to ACTIVE, and replace the legacy files with producer files that carry N_OBS, N_POP and standard errors.
  • Freeze pipeline/bootstrap/: from metadata 0.1.0 onward the CSV files are edited by hand through pull requests (D11).
  • Resolve the decisions that the standard leaves open (see decisions.qmd), including content/SLOTS.csv (gap p).
