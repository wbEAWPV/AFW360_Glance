AFW 360 data standard and producer guidelines

Draft v0.6 · metadata 0.3.0 · SDMX 3.1 (SDMX-ML 3.1.0, SDMX-CSV 2.1.0) · read by the dashboard through afw360

Published

September 29, 2026

This document defines how data for the West Africa Micro Data 360 platform (AFW 360) are structured, coded and documented, how producers create data files, and how the database is extended to new countries, indicators and breakdowns. It follows the SDMX information model (the ISO standard statistical agencies use to exchange data) and borrows the World Bank Data360 dimension layout, stored as plain CSV files in git.

Background on the current inputs is in input-tables-findings.qmd. Nothing here changes the legacy inputs under data_raw/. An R converter produces the new files from them (transition.qmd), and the Python dashboard reads them through the loader package afw360 (D37); the SDMX conformance evidence is on sdmx-conformance.qmd and the FMR workflow on fmr-guide.qmd.

How to read this document. Section 1 is the whole idea on one page: the model, where every file lives, and how the database grows. Read it first. Sections 2 to 12 are reference material; come back to them when you need the exact rule. Section 13 records the design decisions already taken and those still open. Table 1 suggests where to start.

Every table in this document that lists the contents of a metadata file is generated from that file by pipeline/build_docs.R and included from .docs/generated/ (Section 11.1). Those tables cannot drift from the metadata; the prose around them can, and is what to fix if the two disagree.

1 The idea in one page

This standard exists so that every country’s numbers arrive in the same shape. It is written for the country economists and data scientists who prepare indicators from household microdata, and it is what they work from when they add a country, an indicator or a new way of cutting the data. It is also the specification for the developers who build the converter, the validator and the dashboard on top of it.

The database it describes is meant to be a one-stop shop for country-level insight. Every indicator in it comes from national household microdata, and every number is stored the same way for every country.

1.1 One row is one number

Each row of a data file carries one value and the full set of codes that say what that value is: which country, which year, which population, which measure. Those codes fall into two families (Table 2), and telling them apart is the whole model.

The quickest test is the population. If the people behind the categories add up to the whole, as regions or quintiles do, the variable is a breakdown. If every category covers the same whole population again, as the $3.00 and $4.20 poverty lines do, it is a qualifier. N_POP, the population behind each row, makes the test mechanical.

This matters for three reasons. The poverty rate at any line and PPP round is one indicator, POV_HC, not one per line. Every population share is one of three indicators — POP_SH (individuals), POP_HH_SH (households) or POP_HE_SH (enterprises), chosen by what the breakdown counts (D4) — not thirty. And a new grouping such as sector of employment is a row in a codelist, not a change to the file format.

The indicator, its qualifiers and, for a share, the category it is a share of together name a series: “poverty headcount at $4.20 (2021 PPP)” or “share of employed persons working in agriculture”. Every series is one row of SERIES_PLAN.csv, with a stable series_id and a display name, and every data row carries its SERIES_ID (D13). The series is what dashboards, reports and readers think in; the indicator and qualifier codes are how a series is built.

This distinction is the foundation of the database. Every rule in the rest of this document follows from it, and everyone who adds data has to apply it consistently.

1.2 Common compositions, and how each number is checked

Table 3 builds some familiar numbers out of the two families. The last column shows what the coding buys in practice: once a number is coded this way, the validator can check it against related rows.

Everything in the last column reduces to three generic rules, and RULES.csv says which of them apply to which indicator or series (Section 6.13):

  1. Aggregation. Over a partition, totals sum, and means and shares aggregate as N_POP-weighted averages.
  2. Closure. Some qualifiers partition the measured quantity: COICOP divisions sum to 1, and fiscal instruments sum to the total.
  3. Range and order. Shares lie in 0–1, counts are non-negative, and the headcount rises with the poverty line.

Section 2.8 shows these numbers as they are written in a data file.

1.3 Where everything lives

Everything is plain files in one git repository, in ten top-level folders (Listing 1):

  • data_raw/ holds the current legacy inputs, byte-frozen: file names and bytes unchanged, proven by data_raw/CHECKSUMS.sha256 (D2).
  • pipeline/ holds the R code that reads data_raw/ and the plans and writes every other folder: the metadata bootstrap, the converter, the validator and the SDMX generator and importer (D1, D11, D30).
  • metadata/ is the dictionary. It says what every code means, which rows a data file must contain, which rules the numbers must satisfy, and which surveys and program runs the numbers come from. Every other folder refers to it, and every change to it is reviewed (Section 11).
  • data/ holds the numbers: one CSV per country, reference year and estimation method, each with a manifest recording how it was produced and against which metadata version.
  • geo/ holds the boundaries used for maps.
  • content/ and assets/ hold the prose and images the dashboard shows beside the numbers.
  • sdmx/ holds the SDMX-ML structure message and the SDMX-CSV metadata messages, generated from metadata/ and content/, committed and checked for staleness (D28, Section 3.10).
  • tools/ holds tools outside the pipeline: the independent SDMX verification in Python (tools/verify/, D30) and the FMR install notes and scripts (tools/fmr/, D35).
  • afw360/ is the Python package of the dashboard loader, the one place the dashboard reads data from (D37).

Numbers flow one way. A producer’s program computes indicators from the harmonized microdata and writes a data file and its manifest. The validator checks the file against metadata/ (Section 12). The dashboard reads published files through a single loader. Until producers deliver files, the converter does their job: it turns the current Excel tables into data files using LEGACY_LABELS.csv (Annex).

Metadata is generated once, then frozen (D11). The first version of every file under metadata/ was generated by an R script in pipeline/bootstrap/, from hand-written seed tables (pipeline/bootstrap/seeds/*.csv) and a small authored text file (pipeline/bootstrap/text/*.csv). From metadata version 0.1.0 onward, the CSV files under metadata/ are the source of truth and are edited by hand through pull requests; the bootstrap scripts are frozen.

Structural migrations are scripts, run once (D12). When a release changes the columns of a metadata file or of the data file, the change is made by a script under pipeline/migrations/<version>/, committed with the release and run once. The script reads the previous version’s files and writes the new ones, so the change is reviewable and reproducible; it never re-runs the bootstrap. After it has run, hand editing resumes.

The metadata, the converter and the validator exist, and the two countries’ files have been produced from the legacy workbooks (transition.qmd). The dashboard reads them through the loader in afw360/ (D37); no chunk of index.qmd reads data_raw/ any more (Section 7.3).

The 0.3.0 migration (pipeline/migrations/0.3.0/migrate.R) is the worked example of that rule. It refuses to run unless VERSION is the previous release, and it reads authored inputs from pipeline/migrations/0.3.0/inputs/ (the artefact list, the DSD rows, CL_FREQ.csv, COLUMNS_0.3.0.csv, CHANGELOG_0.3.0.md and the alignment table), so the script itself holds no hand-typed names or descriptions. Its choices where the plan was silent: ALIGNMENT.csv has the columns codelist, code_0_2_0, code_0_3_0, name_en, definition_en, global_urn, and an empty name_en or definition_en keeps the previous value (an added code, today only CL_UNIT_MEASURE.XOF, fills both); XOF is appended as the last row of CL_UNIT_MEASURE.csv with status DRAFT; a code rename also rewrites parent and replaced_by references in the same list; the CL_FREQ rows of the alignment table are checked against inputs/CL_FREQ.csv, not applied; in COLUMNS.csv the CL_FREQ block comes before CL_SEX and the ARTEFACTS.csv block after the COLUMNS.csv rows. With --out-root <dir> it writes a complete metadata tree, and diff -r against the committed metadata/ is empty.

1.4 How the database grows

The rule for every extension is metadata first, data last. A number can enter the database only once its codes exist, so every change starts in the codelists and ends with a data file that the validator accepts. If a new number cannot be described with the existing codes, the codes are extended first, in the same pull request as the data.

A new country is added in this order:

  1. Register the country in CL_AREA.
  2. Register its spatial schemes in CL_GEO_SCHEME and their units in CL_GEO.
  3. Check its indicators against the dictionary, CL_INDICATOR. Every country should produce the same set of indicators, matching the dictionary’s codes, definitions and meaning. When a country’s survey cannot match a definition, update the dictionary with a new code linked to the old one through related, rather than stretching an existing code to fit.
  4. Do the same for breakdowns and qualifiers: the country’s categories map to the shared codes in CL_COMP_BREAKDOWN and CL_QUALIFIER.
  5. Describe the survey in SURVEYS.csv, and add the boundary files the maps need.
  6. Produce the data file for each reference year, following TAB_PLAN, together with its manifest.

Section 8.4 gives each step in full.

A new indicator starts in the microdata, not in the aggregation. First standardize the variables it needs in the survey microdata itself, so that each one has the same definition, universe, unit and recall period in every country. Once they are standardized, the indicator is a simple aggregate of them: a mean, a share or a total over each cut. If an indicator needs complicated logic at the aggregation step, its variables are not yet standardized enough.

Every constructed variable also needs its own metadata, recording what the microdata looked like when the indicator was computed from it: the questionnaire module and questions, the recall period, the universe, the units and any recoding. CL_INDICATOR points to these variables through source_questionnaire, source_vars and program. Where the variable-level documentation itself is kept is still an open decision (Section 13.2).

Everything else, such as a breakdown, a qualifier, a poverty line, a spatial scheme, a survey round, a piece of text or a figure, is listed in Table 30 with the files to edit and the version bump it needs. The only structural change is to the columns of the data file, and only the data team makes it (Section 11).

2 Data structure: dataflow AFW360_HH

This section is the contract for the data file: its columns, what may go in each, and which rows it must contain. Read it before writing a producer program, the converter or the dashboard loader.

A dataflow is SDMX’s name for a family of files that share one set of columns and codelists. AFW360_HH covers everything estimated from household-survey microdata: poverty, consumption, jobs, enterprises, agriculture, energy, housing, shocks, social protection, inequality and fiscal incidence. Fiscal incidence is not a separate dataflow. It comes from the same households and the same cuts, and differs only in its qualifiers.

A separate dataflow is needed only when the statistical unit is not the household population at all, for example tax parameters by bracket or macroeconomic series. The rule is: a different statistical unit means a new dataflow; a new source, a new survey round or a model-based estimate means only a new file. A nowcast or microsimulation of the same population is the same dataflow, told apart by the ESTIMATION dimension (Section 2.3).

2.1 Columns

Data files are SDMX-CSV 2.1 data messages (Section 3.2) with exactly 37 columns, in this order (D46): the three fixed SDMX-CSV columns, then the 34 components of Table 4 in DSD order, which are 18 dimensions, TIME_PERIOD, nine measures and six attributes. The role says which family a component belongs to (Section 1.1): breakdowns say who is counted, qualifiers say what is measured, the reference columns say how often, when and how the value was estimated, measures carry the value and its reliability, and attributes describe the value’s identity, unit, status and origin.

Fixed columns. SDMX-CSV requires them in every message. They are not components of the DSD and are not rows of DSD_AFW360_HH.csv.

  • STRUCTURE is always dataflow.
  • STRUCTURE_ID is WB.AFW360:AFW360_HH(<VERSION>), with the content of metadata/VERSION: today WB.AFW360:AFW360_HH(0.3.0).
  • ACTION is R on every row (D38, Section 2.6).

The DATAFLOW column of metadata version 0.2 is gone: STRUCTURE_ID names the dataflow and its version.

The key is the 18 dimensions plus TIME_PERIOD, 19 columns, FREQ through TIME_PERIOD. Together they identify one observation, and no two rows of the database share them. FREQ is the first dimension and is always A, annual, coded by CL_FREQ (D34).

Measures (D33). An observation carries nine measures. OBS_VALUE is the value itself and is mandatory. STD_ERR, CI_LOWER, CI_UPPER, N_OBS and N_POP were attributes in metadata version 0.2 and are now measures; their meaning is unchanged (Section 2.6). Three optional measures are new: N_OBS_NUM, the unweighted number of records in the numerator of a share; DEFF, the design effect; and DF, the degrees of freedom of the variance estimate. None of the three can be derived from the others, and all matter for reliability. N_OBS_NUM is required where STD_ERR is; DEFF and DF are optional until a producer file defines them. Legacy files leave every measure but OBS_VALUE empty.

Attributes. Six attributes describe the observation. Each is attached at a stated level:

  • SERIES_ID is attached to INDICATOR and the ten breakdown and qualifier dimensions, and UNIT_MEASURE to REF_AREA and INDICATOR. Both are repeated on every row and have exactly one value per combination of those dimensions across all data files; the validator checks this (STRUCT.ATTR_LEVEL, Section 12).
  • PRECISION, OBS_STATUS, SOURCE_ID and OBS_COMMENT are attached to the observation. OBS_STATUS also relates to the measure OBS_VALUE.
  • SERIES_ID, UNIT_MEASURE, OBS_STATUS and SOURCE_ID are mandatory and never empty (D39). PRECISION and OBS_COMMENT are optional.

Four of the attributes were added in metadata version 0.2 so that a row can be read without opening any other file (D13 to D16):

  • SERIES_ID names the series the row belongs to (Section 6.12). It is redundant with the key, and the validator checks that they agree. It is an uncoded String: series ids contain ., which SDMX code ids forbid, so no codelist is derived from SERIES_PLAN.csv, and the validator checks every value against that file instead (D43, Section 6.1).
  • UNIT_MEASURE is the unit of OBS_VALUE, resolved for the country: SHARE, PERSON, HA or, for money, the ISO 4217 currency code such as XOF (Section 2.6). All of them are codes of CL_UNIT_MEASURE, which was called CL_UNIT before version 0.3.0 and now lists the currency codes too (Section 3.8).
  • PRECISION is the rounding unit of OBS_VALUE in base units, empty when the value is exact. A legacy conversion of a share rounded to two decimals writes 0.01; a count converted from millions rounded to two decimals writes 10000.
  • SOURCE_ID names the program run that produced the row, in SOURCES.csv (Section 6.15). Its codelist CL_SOURCE is derived from that file (D43).

2.2 The two sentinels

_T and _Z are reserved codes with fixed meanings. They are never listed in a codelist CSV, and no code in any codelist CSV may start with _. The SDMX generator adds them to the generated codelists, because SDMX validators accept only values that exist in the codelist (D42, Section 6.1).

  • _T, total. The value covers every unit and is not split on this dimension. Valid in GEO, SEX, AGE, URBANISATION and the breakdown slots.
  • _Z, not applicable. Valid in every unused qualifier slot, and in SEX or AGE when the indicator is not about individuals. A household-level indicator writes SEX=_Z, not SEX=_T, because “total over both sexes” would be a claim about a dimension that does not apply to households.
  • GEO and URBANISATION are never _Z: every unit lives somewhere.

Three further SDMX sentinels are reserved and not yet used (D21): _U unknown, _O other, and _X not allocated. They exist so that a classification with a residual category can still be a partition that sums to one. No breakdown variable has such a category today; when one does, it uses these codes rather than inventing OTHER or UNKNOWN categories.

2.3 Estimation method

ESTIMATION is a key dimension that says how the value was produced (D17), with the codes of CL_ESTIMATION:

  • SURVEY: a direct estimate from the survey microdata of the reference year.
  • MODEL: a model-based value for the reference year, whether a nowcast, a projection or a microsimulation, built on an earlier survey or on scenario assumptions.

The two can coexist for the same country and year, for example a 2026 nowcast built on the 2021 survey next to the 2026 survey estimate once it exists. Because ESTIMATION is part of the key, the two never collide, and a chart can overlay them. They live in separate files, named AFW360_HH_<ISO3>_<YEAR>_<ESTIMATION>.csv, each with its own manifest and its own source in SOURCES.csv, which records the base survey and the program.

Every row of a MODEL file carries OBS_STATUS=E unless the cell is empty (O) or cannot exist (M). Which series a MODEL file must contain is declared in SERIES_PLAN.csv’s estimation column (Section 6.12); a nowcast typically covers poverty and inequality only.

2.4 Rules for the breakdown columns

  1. Fill the slots from the left, with no gaps. Unused slots are _T.
  2. Use the canonical order. When a row has several breakdowns, they go in ascending slot_order from CL_BRK_VAR, with ties broken alphabetically by var_code. Each combination then has exactly one spelling.
  3. One category per variable per row.
  4. Respect unit compatibility. A breakdown variable may be used only with indicators whose stat_unit appears in its applies_to_units.
  5. Never duplicate a named dimension. Residence, individual sex, individual age and geography always go in their own columns.
  6. SEX and AGE describe the individual being counted, not the household head. The head’s characteristics are breakdown variables (HHH_SEX, HHH_AGE) and go in the slots.
  7. An age band that defines an indicator’s universe is not a breakdown. “Employed, 15–64” has that band in its universe and writes AGE=_T.

2.5 Rules for the qualifier columns

  1. Fill from the left, with no gaps. Unused slots are _Z.
  2. Use the canonical order: ascending slot_order from CL_QUAL_VAR, with ties broken alphabetically.
  3. One category per qualifier variable per row.
  4. A row may use only the qualifiers its indicator declares in INDICATOR_QUALIFIERS.csv (Section 6.14), plus any qualifier required by a breakdown it uses. POOR_Y requires a poverty line, so a food-share row broken down by poverty status carries POVLINE_* and PPP_* even though CONS_SH does not otherwise use them.
  5. Pairings must be allowed: QUALIFIER_PAIRS.csv says which PPP rounds go with which line (Section 6.14).

2.6 Values and attributes

  • Store OBS_VALUE unrounded, with . as the decimal separator and no thousands separator or % sign. Rounding is a display decision (display_as, decimals).
  • Use base units. Shares are 0–1, never 0–100. People are counted in persons, not millions. Money is in whole currency units.
  • UNIT_MEASURE repeats the indicator’s unit_measure on every row, so the file can be read without the dictionary (D14). The dictionary stays country-neutral: a money indicator has unit_measure = LCU there, and the data row resolves it to the country’s currency from CL_AREA, so a Senegal row says XOF. Every other unit is copied as is. The validator checks the two agree.
  • PRECISION is empty for a value written unrounded, which is every value a producer delivers (D15). Only a conversion from an already-rounded source fills it, with the rounding unit in base units: 0.01 for a share rounded to two decimals, 10000 for a count that was published in millions with two decimals. The validator’s tolerances and the dashboard’s display cap read it (Section 7.3).
  • SOURCE_ID names the program run that produced the row, registered in SOURCES.csv (D16, Section 6.15). A file may hold rows from several sources, for example poverty from one program and fiscal incidence from another; the manifest lists them all.
  • Do not suppress. Every estimate is published whatever its sample size. Reliability travels with the value instead: N_OBS and N_POP are required on every row, STD_ERR and the confidence interval on every row whose statistic admits them, and the dashboard shows them (Section 7.3). A value that rests on too few records is flagged OBS_STATUS=U, not hidden (below).
  • N_OBS is the unweighted number of records of the estimation file used: records in the group, in the indicator’s universe, with a non-missing value. When a person-weighted poverty rate is computed on a household file, N_OBS counts households. SURVEYS.analysis_units records which file each stat_unit is estimated from, so a reader always knows what N_OBS counts.
  • N_POP is the sum of weights over those same records: the population, households or enterprises the value refers to.
  • On a share row, both counts are the denominator (D19). “Share of employed persons working in agriculture, poorest quintile” is estimated as a mean over employed persons in the quintile, and N_OBS and N_POP are the records and weighted population of that universe, not of the agricultural workers. The group is the population cut, quintile; the defining breakdown, sector, is what is measured. The agricultural workers’ own population is OBS_VALUE × N_POP by definition, so it is not stored. The partition checks of Section 12 therefore run over population cuts only, never over a series’ defining breakdown.
  • Standard errors and confidence intervals must reflect the survey design (weights, strata and PSUs, with linearized variance). Intervals are at 95%.
  • Rows from a legacy conversion carry PRECISION and no reliability measures, because the workbooks hold neither. The exemption is a property of the source: the reliability columns are required on every row whose source has kind = PRODUCER, and may be empty where it has kind = LEGACY_CONVERSION (Section 7.2).
  • Missing values (D39). OBS_VALUE is NaN on every row whose OBS_STATUS is O or M, and a number on every other row. NaN is the SDMX-CSV value for an intentionally missing float or double; #N/A, the value for every other type, is not used. An optional measure or attribute that the source cannot supply is left empty, which SDMX-CSV reads as “not provided”. The mandatory attributes SERIES_ID, UNIT_MEASURE, OBS_STATUS and SOURCE_ID are never empty.
  • ACTION is R (replace) on every row of a published file (D38). R replaces whole observations and merges attributes above observation level; it does not delete observations missing from the file. A consumer that replaces a slice deletes it first, so a published file contains no D rows (Section 3.2).

OBS_STATUS takes one of the codes in Table 5, which come from the SDMX cross-domain CL_OBS_STATUS. A cell that can never exist is normally declared in the indicator’s excluded_breakdowns (Section 6.2) and left out of the file. M covers such a cell when it has not been declared there: the row stays, with OBS_VALUE = NaN, so the gap is visible.

Two of the codes are set by a rule rather than by judgement (D22):

  • U, low reliability, applies when N_OBS is below the dataflow’s minimum, or when the coefficient of variation STD_ERR / |OBS_VALUE| exceeds the dataflow’s maximum for a statistic that admits a standard error. Both thresholds are rows of RULES.csv with scope DATAFLOW (RELIABILITY_MIN_NOBS, initially 30, and RELIABILITY_MAX_CV, initially 0.30). The producer writes the code, and the validator recomputes it and reports a mismatch as an error. A row with no N_OBS and no STD_ERR, as in a legacy conversion, is never U.
  • D, definition differs, applies to every row of a series that a country produces with a definition that departs from the dictionary’s. It is allowed only where SERIES_PLAN.csv has a row for that country and series with status = DEVIATES (Section 6.12), and is required on every row of such a series.

One code per row. When several apply, the first of M, O, E, D, U, A in that order is written. A model-based value that would also fail the reliability rule is therefore E, and its standard error stays visible for the reader’s own judgement. Q, suppressed, is registered so that the code exists if a statistical office’s confidentiality rule ever has to be honoured; nothing in the database uses it today, and the no-suppression policy stands.

2.7 Which rows exist

plans/SERIES_PLAN.csv is the explicit list of series to produce: one row per series_id, naming its ref_area, INDICATOR, the qualifier combination in MEASURE_QUALS and, for a share indicator, the category it is a share of in DEFINING_BREAKDOWN (Section 6.12). A plain Cartesian product of qualifiers over cut categories over-generates — CONS_SH crossed with COICOP and poverty status gives 39 combinations where only 15 are real — so SERIES_PLAN states the real ones instead.

A series row with ref_area = ALL applies to every country. A row for a specific country overrides the ALL row for the same series_id and carries that country’s status: NOT_PRODUCED when the survey cannot support the series, in which case no rows are required, or DEVIATES when the country produces it under a definition that departs from the dictionary’s, in which case the rows are required and carry OBS_STATUS=D (D23). The estimation column says in which kind of file the series is expected, SURVEY, MODEL or both.

For each applicable SERIES_PLAN row whose estimation includes the file’s ESTIMATION and whose status for the country is not NOT_PRODUCED, the required data rows are:

(the cuts in TAB_PLAN compatible with the indicator’s stat_unit, found through CL_BRK_VAR.applies_to_units rather than a unit column on TAB_PLAN itself — geography and urbanisation cuts apply to every unit) × (the categories of those cuts) − (anything listed in excluded_breakdowns) − (cells withheld in LEGACY_OVERRIDES.csv)

The coverage generator writes SEX=_Z and AGE=_Z, not _T, wherever TAB_PLAN says sex = _T / age = _T but the indicator’s stat_unit is not IND (Section 2.2). It also keeps each generated row’s provenance — its cut_id and defining breakdown — so that a check such as “the parent of a row” (Section 12) is computed from that provenance rather than guessed from the row’s codes in general.

Nothing extra, nothing missing. A cell with no observations is a row with OBS_STATUS=O, not an absent row. This is what makes a file checkable: the validator can compute the set of rows that should exist and compare it with the rows that do.

A cell known to be wrong is different again: it is withheld, not published. Its row is absent from the file, the exclusion is registered in metadata/plans/LEGACY_OVERRIDES.csv (action WITHHOLD, with a reason and evidence), and the coverage check reads the register and subtracts it from the required rows (D5). Action COMMENT is not a withholding: the value is kept, OBS_COMMENT is set, and the row still counts as required.

3 SDMX conformance

This section says how the database maps onto SDMX. The project targets the SDMX 3.1 family: SDMX-CSV 2.1.0 for data and reference metadata, and SDMX-ML 3.1.0 for structures (D27). No SDMX-JSON is produced (D29).

The CSV files under metadata/, content/ and data/ remain the source of truth. The SDMX-ML structure message and the SDMX-CSV metadata messages are generated from them, committed, and checked for staleness like the generated tables of this document (D28, D20). Nobody edits the XML by hand. The pipeline stays in R: R writes the XML and validates it against the SDMX-ML XSDs. Python is used only by the dashboard loader and by a separate verification tool that is never part of the pipeline (D30).

3.1 Identity and versioning

  • Agency. Every artefact is maintained by WB.AFW360, a sub-agency of the registered World Bank agency WB (D31).
  • Agency scheme. The project ships a WB:AGENCIES agency scheme (fixed id, no version attribute in XML) that declares one agency, AFW360, named “West Africa Micro Data 360 (AFW DIP/POV team)”. It is a local placeholder so that WB.AFW360 resolves in FMR, pysdmx and the XSD and URN checks. It asserts nothing in the World Bank’s namespace and is never submitted to any registry. At registration it is replaced by the World Bank’s own scheme. Before loading into a World Bank registry, check whether WB:AGENCIES already exists there; if it does, have AFW360 added to it and drop the local copy. Global registration is a later step, taken by the World Bank’s SDMX owner.
  • Version. Every maintainable artefact carries agencyID="WB.AFW360" and version="0.3.0", the content of metadata/VERSION (D40).
  • Semver dependency rule. A semver artefact references only semver artefacts (IM technical notes, Annex “Semantic Versioning”, “Dependency Management”; the XSD does not enforce it). The one exception is a reference to an item of the fixed-version organisation schemes, AGENCIES, DATA_PROVIDERS and METADATA_PROVIDERS, whose URN version is (1.0). The XSD requires those references, and the SDMX.URN check exempts them. Annotation values such as GLOBAL_CODE and SDMX_CROSS_DOMAIN_CONCEPT are not structural references.
  • URN form. urn:sdmx:org.sdmx.infomodel.<package>.<Class>=WB.AFW360:<ID>(0.3.0). A code appends .<CODE>.
  • Short reference form, used in CSV messages: WB.AFW360:<ID>(0.3.0).
  • Message header sender id: WB_AFW360. Sender ids are plain IDs and cannot contain a dot.
  • Artefact ids are NCNames: a letter, then letters, digits, _ or -. The project code rules (Section 6.1) are stricter and stay.
  • Released artefacts are immutable. A released X.Y.Z never changes (SDMX semantic versioning). Edits between releases are made on a -draft copy and re-imported into the CSVs; the next release bumps VERSION and regenerates every artefact (D40, Section 11).

Rules:

  • 37 columns, in the order of the DSD file’s position column (D46): the three fixed columns, the 18 dimensions, TIME_PERIOD, the nine measures, then the six attributes. The key is the 18 dimensions plus TIME_PERIOD, 19 columns (Section 2.1). The header is one physical line.
  • STRUCTURE is always dataflow. STRUCTURE_ID is WB.AFW360:AFW360_HH(<VERSION>).
  • ACTION is R, replace, in every published file (D38). The SDMX-CSV 2.1 guide recommends R for complete query responses; I and A are deprecated. R replaces whole observations and merges attributes above observation level. It does not delete observations missing from the file. A consumer that replaces a slice deletes it first, with a D row of the partial key REF_AREA, ESTIMATION, TIME_PERIOD. The published files contain no D rows.
  • FREQ is A.
  • Missing values (D39). OBS_VALUE is NaN when OBS_STATUS is O or M, and a number otherwise. NaN is the SDMX-CSV intentionally-missing value for float and double components only. #N/A is the value for every other type and is not used. Optional measures and optional attributes are left empty when not available; in SDMX-CSV, empty means “not provided”. The mandatory attributes SERIES_ID, UNIT_MEASURE, OBS_STATUS and SOURCE_ID are never empty. The validator enforces the rule through VALUE.NUMERIC (which accepts NaN) and VALUE.STATUS_EMPTY (an error on NaN or empty under a status other than O or M, and on a number under O or M). It still accepts an empty OBS_VALUE on an O or M row as missing, because older coverage tests build such rows; enforcing “NaN only” is left to a later validator change. The published files carry NaN on every such row.
  • Attributes on partial keys. SERIES_ID and UNIT_MEASURE are attached to partial keys, replicated on every row, and carry exactly one value per partial key across all data files: SERIES_ID per INDICATOR and the ten breakdown and qualifier dimensions, UNIT_MEASURE per REF_AREA and INDICATOR. The validator check STRUCT.ATTR_LEVEL (ERROR) groups all rows of all files by each attribute’s relationship dimensions and reports any group with more than one distinct value.
  • Numbers use . as the decimal separator and no thousands separator.
  • Encoding. RFC 4180 quoting, written with readr::write_csv(..., na = ""), so readr’s default NA never appears. UTF-8 without BOM, LF line endings. LF is a project convention and a documented deviation from RFC 4180, which specifies CRLF; the SDMX-CSV 2.1 guide does not address line endings or BOM.
  • File names are unchanged: AFW360_HH_<ISO3>_<YEAR>_<ESTIMATION>.csv.
  • Manifest. The key dataflow becomes structure_id and keeps its slot; a new key sdmx_csv_version, holding 2.1.0, follows it; the other 15 keys keep their order, 17 keys in all (Section 6.10). The validator reports a wrong value of either key as COVER.MANIFEST, with row key key=structure_id or key=sdmx_csv_version. The manifest stays a project-level sidecar; it describes a file, which is not an SDMX artefact.

3.3 Data structure definition DSD_AFW360_HH

The dataflow WB.AFW360:AFW360_HH(0.3.0) references the data structure definition WB.AFW360:DSD_AFW360_HH(0.3.0). Its components are the rows of metadata/structure/DSD_AFW360_HH.csv, listed in Table 4, which is generated from that file and is authoritative. Table 7 summarises them in data-file order. The three fixed SDMX-CSV columns are not components and are not rows of the DSD file.

  • Pos is the CSV column order only. In SDMX-ML the writer emits DimensionList (rows 1 to 19), then AttributeList (rows 29 to 34), then MeasureList (rows 20 to 28), as the XSD requires.
  • Usage and requiredness. The project’s requiredness (R, C, O) and its conditions are unchanged. For example, STD_ERR is required on rows of a PRODUCER source where the statistic admits it. They stay in the DSD file’s required column and in the validator. SDMX usage is the weaker, structural statement. Of the three new measures, N_OBS_NUM is C with the same condition as STD_ERR, and DEFF and DF are O until a producer file defines them.
  • Concept identity. Every component has a concept of the same id in CS_AFW360 (Section 3.5).
  • Time. The time dimension’s representation is written explicitly, TextFormat textType="GregorianYear".
  • No MSD link. The DSD does not reference the metadata structure, because data-related reference metadata is not used.
  • The DSD file. DSD_AFW360_HH.csv has the columns position, id, component, role, name_en, codelist, data_type, usage, relationship, measure_relationship, required, sentinel, min_value, max_value, description, one row per component (34). relationship is observation or a space-separated list of dimension ids, written out in full (COMP_BREAKDOWN_1 to COMP_BREAKDOWN_5, MEASURE_QUAL_1 to MEASURE_QUAL_5) with no “dimensions:” prefix; the prefix in Table 7 is for reading only. data_type is empty on coded components. min_value is 0 on STD_ERR, N_OBS, N_POP, N_OBS_NUM, DEFF, DF and PRECISION. required keeps the earlier values, with FREQ R, N_OBS_NUM C, DEFF O and DF O.
  • What is written. 18 dimensions and one time dimension (GregorianYear), six attributes, nine measures and one MeasureRelationship (OBS_STATUS to OBS_VALUE). No ConceptRole is written: the project role (breakdown, qualifier, reference) stays in the DSD file.

3.4 Codelists and the CSV-to-SDMX mapping

Every metadata/codelists/CL_*.csv becomes a codelist WB.AFW360:CL_*(0.3.0). Columns map to SDMX by convention, with no mapping file to maintain (D41). The mapping is mechanical and reversible, which the FMR round-trip needs.

The annotation registry. An annotation is written as Annotation id="<type>", with AnnotationType the type and AnnotationValue the value. Annotations are the first child of the code. An empty cell produces no annotation. Each annotation is written on one line of the XML, so grep -c counts them. The 0.3.0 message holds 22 codelists with 299 codes (eight of them sentinels), 32 GLOBAL_CODE annotations (27 filled global_urn cells plus five sentinels) and 11 SDMX_CROSS_DOMAIN_CONCEPT annotations. The annotation types in use are:

  • GLOBAL_CODE: the full code URN of the matching code in a global list (Section 3.8).
  • AFW_<COLUMN>: one per codelist column that has no SDMX slot, including AFW_STATUS, AFW_VERSION_ADDED, AFW_REPLACED_BY and AFW_NOTES.
  • AFW_SENTINEL: Y on a sentinel code added by the generator.
  • AFW_SOURCE_FILE and AFW_METADATA_VERSION: the repository path of the CSV an artefact was generated from, and the metadata version. Every maintainable carries AFW_METADATA_VERSION; AFW_SOURCE_FILE is left out where ARTEFACTS.csv has no source_file (the organisation schemes, the dataflow, the metadataflow and the two agreements). Maintainables carry no AFW_STATUS: the status column of ARTEFACTS.csv is not exported.
  • SDMX_CROSS_DOMAIN_CONCEPT: on a concept that matches an SDMX cross-domain concept (Section 3.5).

Special cases:

  • CL_GEO_SCHEME.csv is keyed by ref_area and code. Its SDMX code id is <ref_area>_<code>, for example SEN_ADM1, and the two parts are also kept as the annotations AFW_REF_AREA and AFW_CODE. The importer splits the id on the first underscore.
  • Sentinels (D42). The generator appends _T (“Total”) and _Z (“Not applicable”) as real codes, reading the DSD file’s sentinel column: _T to CL_GEO; _T and _Z to CL_SEX and CL_AGE; _T to CL_URBANISATION and CL_COMP_BREAKDOWN; _Z to CL_QUALIFIER. That is eight sentinel codes in all. Each carries AFW_SENTINEL = Y, which the importer uses to drop it again. Five of them also carry one GLOBAL_CODE, the matching code in the list’s own global counterpart: CL_SEX _T and _Z point to SDMX:CL_SEX(2.1)._T and ._Z; CL_AGE._T points to IAEG-SDGs:CL_AGE(1.25)._T, CL_URBANISATION._T to IAEG-SDGs:CL_URBANISATION(1.10)._T, and CL_COMP_BREAKDOWN._T to IAEG-SDGs:CL_QUANTILE(1.1)._T. All of these are written as full code URNs. The other three, CL_AGE._Z, CL_GEO._T and CL_QUALIFIER._Z, have no matching code in their own list’s global counterpart and carry no GLOBAL_CODE. The sentinels still never appear in the codelist CSVs (Section 6.1).
  • Full URNs. GLOBAL_CODE and global_urn values are always full code URNs, urn:sdmx:org.sdmx.infomodel.codelist.Code=<agency>:<id>(<version>).<code>, never the short form.
  • Derived codelists (D43). Three registries become codelists. CL_SOURCE comes from registries/SOURCES.csv, named by source_id, described by notes. CL_SURVEY comes from surveys/SURVEYS.csv, named by survey_name. CL_FIGURE comes from registries/FIGURES.csv, named by title_en. CL_SOURCE and CL_SURVEY codes carry only id, name, description and AFW_STATUS; CL_FIGURE codes carry id and name only, with no AFW_STATUS. Every other column goes to a metadataset (Section 3.6). With the 19 codelists generated from the codelist CSVs, that makes 22 codelists, among 32 artefacts in all. This gives SOURCE_ID a real codelist. SERIES_PLAN.csv derives no codelist: series ids contain ., which the SDMX IDType for code ids forbids, so SERIES_ID stays an uncoded String whose values the validator checks against SERIES_PLAN.csv (Section 6.1).
  • Names and descriptions of artefacts come from metadata/structure/ARTEFACTS.csv (D44). It lists every SDMX artefact to generate, one row each, with artefact_id, artefact_type (the SDMX class name), agency_id, source_file, name_en, description_en, status, version_added and notes. The generator iterates over it, so the list of what to generate is data, not code.

3.5 Concepts

The concept scheme CS_AFW360 has one concept per component id of Table 7, from FREQ to OBS_COMMENT. The five COMP_BREAKDOWN_n and the five MEASURE_QUAL_n are separate concepts. It also has one concept per metadata attribute of the MSD (Section 3.6).

  • A component’s concept takes its name and description from the DSD file (name_en, description). A metadata attribute’s concept takes them from COLUMNS.csv: the column humanised as the name, and description as the description.
  • The scheme holds 82 concepts: 34 for the components and 48 for the metadata attributes. Concept ids are shared between the DSD and the MSD: REF_AREA, TIME_PERIOD and NOTES recur and are defined once (the first definition wins, DSD components first), and SOURCE is both a parent of the MSD and the concept of the FIGURES.csv column source. The four parent concepts SURVEY, SOURCE, TEXT and FIGURE have no rows in COLUMNS.csv, so the generator gives them a fixed name and description and no core representation.
  • A concept that matches an SDMX cross-domain concept carries the annotation SDMX_CROSS_DOMAIN_CONCEPT, whose value is the full concept URN in SDMX:CROSS_DOMAIN_CONCEPTS(2.0), for example urn:sdmx:org.sdmx.infomodel.conceptscheme.Concept=SDMX:CROSS_DOMAIN_CONCEPTS(2.0).FREQ (the same full-URN rule as GLOBAL_CODE). All eleven targets exist in that scheme (checked against a copy fetched once): FREQ, REF_AREA, TIME_PERIOD, OBS_VALUE, OBS_STATUS, UNIT_MEASURE, SEX, AGE, INDICATOR, OBS_COMMENT (to COMMENT) and SOURCE_ID (to DATA_SOURCE).
  • Core representation: a coded concept references its codelist; a numeric one carries the TextFormat of Table 7; a text one is String. SERIES_ID is not coded, so its concept is String (Section 6.1). TIME_PERIOD carries TextFormat textType="GregorianYear", the same as its time-dimension local representation.

3.6 Reference metadata

Documentary metadata goes where SDMX puts it: in metadatasets of a metadata structure (D43).

  • MSD WB.AFW360:MSD_AFW360(0.3.0) has four presentational parent attributes, SURVEY, SOURCE, TEXT and FIGURE. Each parent is isPresentational="true", minOccurs="0", maxOccurs="1", with no LocalRepresentation, because the XSD default for minOccurs is 1 and each metadataset fills only one parent. Each parent has one child per source column, minus the id and status columns, with ids equal to the column names upper-cased. Children have TextFormat textType="String", minOccurs="0" and maxOccurs="1".
    • SURVEY: 23 children from SURVEYS.csv (REF_AREA, TIME_PERIOD, SURVEY_NAME, … NOTES).
    • SOURCE: 12 children from SOURCES.csv (every column except source_id and status, so NOTES is included).
    • TEXT: 7 children from content/TEXT.csv: SLOT, REF_AREA, TIME_PERIOD, ORDER, TITLE, BODY, UPDATED_ON. BODY holds the Markdown source: the body cell, or the content of the file named in file (relative to content/text/, CRLF changed to LF, trailing newline kept); file wins over body, and file itself has no child.
    • FIGURE: 15 children from FIGURES.csv (REF_AREA … NOTES, excluding figure_id and status).
    That is 57 children and 61 MetadataAttribute elements in all. Each child’s concept is the CS_AFW360 concept of the same id. Child ids repeat across parents (REF_AREA and TIME_PERIOD under SURVEY, TEXT and FIGURE; FIGURE.SOURCE shares its id with the parent SOURCE), which the XSD allows because ids need only be unique among siblings. The shared REF_AREA and TIME_PERIOD concepts keep their coded or GregorianYear core representation; the MSD overrides it locally with String.
  • Metadataflow MDF_AFW360 has the structure MSD_AFW360 and four explicit Target elements, one per targeted artefact: the codelists CL_SURVEY, CL_SOURCE and CL_FIGURE, and the dataflow AFW360_HH, each as a full URN with version 0.3.0. Wildcard targets are schema-valid but not used. The generator rewrites the versions at each release, like every other reference.
  • Metadatasets, one per registry row, are written as SDMX-CSV 2.1 metadata messages under sdmx/metadata/. The header is MDSTRUCTURE,MDSTRUCTURE_ID,METADATASET_ID,TARGET_TYPES,TARGET_IDS, then the attribute columns. MDSTRUCTURE is metadataflow and MDSTRUCTURE_ID is WB.AFW360:MDF_AFW360(0.3.0). Presentational parents have no column; each child appears as <PARENT>.<CHILD>, for example SURVEY.SURVEY_NAME. Metadatasets are not versioned.
  • Targets are whole artefacts, as the SDMX-CSV 2.1 metadata guide defines them: TARGET_TYPES is a REST structure resource name and TARGET_IDS is AGENCY:ID(VERSION). The guide has no form that targets a single code. The item a metadataset describes is identified by its METADATASET_ID and by the key attributes inside it, such as SURVEY.REF_AREA and SURVEY.TIME_PERIOD. TEXT.csv rows are metadatasets about a country; they target the dataflow and name the country in TEXT.REF_AREA.

The metadata files are written with every field quoted, because the guide recommends quoting every textual value and every MSD attribute is String. The writer turns missing values into "" first, because readr::write_csv(quote = "all") would leave NA unquoted. The header is the five fixed columns, then the dotted MSD children; the id, status and file columns have none. The 0.3.0 files hold 2 rows (MDS_SURVEYS.csv), 2 (MDS_SOURCES.csv), 8 (MDS_TEXT.csv, from content/TEXT.csv) and 1 (MDS_FIGURES.csv).

pysdmx 1.20.0 has no SDMX-CSV metadata reader (Format.REFMETA_SDMX_CSV_2_1_0 exists, but no reader uses it), so the independent check of these files is a header check in tools/verify/verify_sdmx.py. That check is weaker than the rules above: it matches each header cell against the MSD attribute ids by the last dotted segment only, and it does not check MDSTRUCTURE_ID, TARGET_TYPES or the uniqueness of METADATASET_ID. The project validator’s SDMX.STALE check covers those rules, because it regenerates the files and compares them byte for byte. FMR does not read them either: its SDMX-ML 3.0 profile has no MSD (Section 3.11).

3.8 Global alignment

Project codes are aligned to global code values where a global list exists (D32). Alignment is by value where the project code rule allows, and otherwise by the global_urn column, which becomes the GLOBAL_CODE annotation. The global lists cannot be referenced or extended: they carry legacy, non-semver versions, and a semver artefact may not reference a legacy-versioned one (Section 3.1).

Every global_urn is a full code URN. The alignment was fetched once and committed as pipeline/migrations/0.3.0/inputs/ALIGNMENT.csv; the migration reads that table and makes no network call.

Project-only metadata stays CSV and is documented as tooling metadata outside SDMX (D45): TAB_PLAN.csv, SERIES_PLAN.csv, RULES.csv, INDICATOR_QUALIFIERS.csv, QUALIFIER_PAIRS.csv, the LEGACY_* files, COLUMNS.csv, DSD_AFW360_HH.csv itself and the manifests. 3.10 The generated sdmx/ folder

pipeline/build_sdmx.R reads metadata/ and content/ and writes sdmx/:

sdmx/
  README.md                            what is here, how it is generated, how to load it into FMR
  structures/AFW360_structures.xml     one SDMX-ML 3.1 structure message with every artefact
  metadata/MDS_SURVEYS.csv             SDMX-CSV 2.1 metadata messages (D43)
  metadata/MDS_SOURCES.csv
  metadata/MDS_TEXT.csv
  metadata/MDS_FIGURES.csv
Rscript pipeline/build_sdmx.R --root .           # rewrite sdmx/
Rscript pipeline/build_sdmx.R --root . --check   # exit 1 if any file under sdmx/ is stale

Staleness rule. The files under sdmx/ are committed with the metadata that produced them. The output is deterministic: the message header has the fixed id AFW360_STRUCTURES, the sender WB_AFW360 and a prepared timestamp (--timestamp, default 2026-01-01T00:00:00Z), so the same CSVs always give the same bytes. --check regenerates into a temporary folder, compares bytes and prints one line per file (five lines). The repository has no CI: whoever changes metadata/ or content/ runs build_sdmx.R --check (or validate.R, whose SDMX.STALE check does the same) before committing, and a reviewer reruns it on the pull request, in the same way as for a stale table of this document (D28, D20). Outputs built with a custom --timestamp are reported stale. Nobody edits sdmx/ by hand.

The validator’s SDMX module (pipeline/R/validate_sdmx.R, Section 12) holds six checks:

  • SDMX.STALE (ERROR): regenerates the structure message and the four MDS_*.csv files with the default timestamp into a temporary folder and compares every file under sdmx/ except *.md; a differing, missing or unexpected file is a finding.
  • SDMX.XSD (ERROR): the message is valid against the SDMX-ML 3.1 XSDs vendored in pipeline/xsd/sdmx-ml-3.1/; one finding per libxml2 error.
  • SDMX.URN (ERROR): every urn:sdmx: reference outside annotations resolves to a maintainable, or a direct-child item of one, in the same message; every Parent exists; a sub-agency A.B is declared as agency B in a scheme of A; and every reference from a semver artefact points at a semver artefact, except the (1.0) organisation schemes and their items. Component-level URNs do not occur today and would be reported unresolved.
  • SDMX.IDENT (ERROR): every maintainable has agencyID WB.AFW360 (WB for AGENCIES), a version equal to metadata/VERSION (absent on the three fixed-version schemes), an id valid for the XSD IDType, and a non-empty English name.
  • SDMX.CSV_HEADER (ERROR): each data file’s header equals the 37 data columns, and every STRUCTURE_ID is WB.AFW360:AFW360_HH(<VERSION>).
  • SDMX.SKIPPED (INFO): reported once when the root has no sdmx/ folder, like DOCS.SKIPPED; SDMX.XSD, SDMX.URN and SDMX.IDENT then report nothing.

Every validator run sources the SDMX writers, regenerates the outputs and validates them against the XSD, which adds a few seconds; a copy of the repository used as --root therefore needs pipeline/R and content/. The message is parsed from its bytes, not its path (libxml2 on Windows kept the file locked after a failed parse).

Verification tools outside the pipeline. tools/verify/ is an independent reader in Python (pysdmx 1.20.0, venv under tools/verify/.venv), used by reviewers and never by the pipeline (D30):

  • verify_sdmx.py --root . reads the structure message and prints the maintainables by class (32 artefacts), reads each data file as SDMX-CSV 2.1 and prints its observation count (3003 for SEN, 2268 for GNB), header-checks the four metadata messages, and exits 1 on any failure. pysdmx 1.20.0 cannot read com:AnnotationValue, which the XSD allows and this project uses, so the tool validates the original bytes against the schema and hands pysdmx a copy without annotation values. It calls the SDMX-CSV 2.1 reader directly, because read_sdmx sniffs the format and gives a generic error on a bad header. read_sdmx(validate=True) validates against pysdmx’s bundled schemas, not pipeline/xsd/.
  • xsd_validate.py <xsd> <xml> validates with lxml against the vendored XSDs and prints valid or the first error.
  • check_urns.py <xml> resolves every WB.AFW360 URN inside the message and prints unresolved: <n>; a maintainable without a version attribute (the organisation schemes) is registered under version 1.0, items included.

pipeline/reconcile.R checks every cell of the data files against the legacy workbooks. It keeps private copies of the few io.R helpers it needs, so it stays independent of the pipeline’s reader, and still sources codes.R for slot filling. The projection test in pipeline/tests/testthat/ (test-projection-*.R) maps each new data file back onto the 31 columns of the previous layout and compares it with the committed old file; the only allowed differences are the removed DATAFLOW column and NaN against empty on the O rows.

pipeline/import_sdmx.R does the reverse of the generator: it reads an SDMX-ML 3.0 or 3.1 structure message and shows (--diff) or writes (--apply) the changes to the CSVs under metadata/. --apply rewrites all 20 target files (19 codelist CSVs and ARTEFACTS.csv), changed or not. What flows back is listed in Section 3.11.

3.11 Editing and validating with FMR

The Fusion Metadata Registry (FMR) can load the structure message, validate data files against it, and edit artefacts. It is optional: everything is published as plain files in the repository, and no live registry or REST service is run for the dashboard (D36). FMR is installed (D35), without Docker: FMR 12.4.2 as the WAR of Apache Tomcat 10.1.60, on Java 21 (Azul Zulu 21.0.12.1), with a portable MySQL 8.0 database, all under the gitignored tools/fmr/runtime/. The exact install, start and stop steps are in fmr-guide.qmd; the scripts are in tools/fmr/.

FMR 12.4.2 does not read SDMX-ML 3.1. Loading sdmx/structures/AFW360_structures.xml returns HTTP 400 with FMR error 150, “Unrecognised file format”. The generator therefore has a second output profile: Rscript pipeline/build_sdmx.R --root . --out-root <dir> --sdmx-ml-version 3.0 writes the same artefacts with the SDMX-ML 3.0 namespaces, without the MSD, the metadataflow and the metadata provision agreement (whose 3.0 XML differs). It writes only the structure message and only under an --out-root other than the root, and refuses --check. The 3.1 file stays the canonical committed output; the 3.0 profile is written to tmp/ for loading. The data files need no change: FMR accepts the SDMX-CSV 2.1 files as they are (it labels them “SDMX CSV v2.0”) and validates them without error.

The agency WB must exist first. FMR resolves WB:AGENCIES(1.0) against its own SDMX:AGENCIES(1.0) scheme, so the top-level agency WB has to be registered there before the project’s structures load (otherwise HTTP 404, error 100, “Could not resolve reference”). tools/fmr/fmr_load.R does this once, idempotently, by posting tools/fmr/agencies_bootstrap.xml.

The workflow is:

  1. Rscript pipeline/build_sdmx.R --root . generates sdmx/.
  2. Rscript tools/fmr/fmr_load.R --root . checks that FMR answers, registers WB when missing, builds the 3.0 profile into tmp/fmr/v30/ and loads it (action REPLACE, so a reload is harmless).
  3. Rscript tools/fmr/fmr_validate.R --root . posts each data file to /ws/public/data/validate and saves the report as tmp/fmr/<ISO3>_<YEAR>_<ESTIMATION>_validation.json. A clean report has "Errors":false; that field is the test, not the absence of the word “error”. Steps 1 to 3 are all that validation-only use needs.
  4. To edit, work in FMR on a copy versioned <next>-draft, then export with Rscript tools/fmr/fmr_export.R --root . --out tmp/fmr/export.xml. FMR exports SDMX-ML 3.0 only (a request for 3.1 returns HTTP 406) and rewrites the message header. Run Rscript pipeline/import_sdmx.R --root . --diff tmp/fmr/export.xml to see the changes against the CSVs, then --apply, and commit through a pull request. At release, bump VERSION, regenerate sdmx/ and reload (Section 11).

What flows back from FMR. An unedited export round-trips with no change (299 codes, 2371 annotations, 399 descriptions). The importer brings back codes, names, descriptions, parents and annotations of the 19 CSV codelists, and the names and descriptions of the other artefacts in ARTEFACTS.csv. It does not bring back: the ARTEFACTS.csv columns status, version_added, notes, agency_id and source_file; edits to the derived codelists CL_SOURCE, CL_SURVEY and CL_FIGURE (reported, never written; edit their registries instead); AFW_METADATA_VERSION; the structure of the concept scheme, DSD, MSD, dataflow and agreements; non-English names; sentinel names and their GLOBAL_CODE, which are dropped with the sentinel. The MSD, metadataflow and metadata provision agreement are not in the 3.0 profile at all. A code added in FMR to a codelist whose CSV has no COLUMNS.csv rows stops the import. The importer reads SDMX-ML 3.0 and 3.1 alike and falls back to AnnotationTitle when AnnotationValue is absent. FMR’s submit and error responses are always SDMX-ML 2.1.

4 Breakdowns

Read this before adding a new way of splitting the population.

A breakdown variable classifies units: sex of household head, consumption quintile, sector of employment, poverty status. It is one row in CL_BRK_VAR. Its categories are rows in CL_COMP_BREAKDOWN, and each category code begins with its variable code.

Adding one changes no structure. It takes a row in CL_BRK_VAR, a row per category in CL_COMP_BREAKDOWN, and a line in TAB_PLAN.

4.1 Initial breakdown variables

Table 11 lists the registered breakdown variables with their categories. It is generated from CL_BRK_VAR.csv and CL_COMP_BREAKDOWN.csv. A variable whose universe reads TBD is registered from a legacy label whose population the producer has not yet confirmed; it stays DRAFT until then.

slot_order values are spaced by 10 so that new variables can go in between, as DEC_MKT (15) and EMP_STATUS (55) already do. slot_order is immutable once the variable is ACTIVE: the key of every crossed row depends on it, so changing it would change the identity of existing observations.

DEC_MKT is registered for fiscal-incidence work, where households are ranked by market income; QUINT ranks them by consumption per capita. Two different rankings are two different variables, and each states its basis in definition_en.

4.2 Every breakdown variable carries a universe

CL_BRK_VAR.universe names the population that the categories partition. This is what makes each of POP_SH, POP_HH_SH and POP_HE_SH work as a single indicator for its stat_unit: the share is the category’s weighted count divided by the universe’s, and the row’s N_POP is the universe’s (Section 2.6). “Share of employed in agriculture” (individuals, POP_SH) and “share of households with two enterprises” (households, POP_HH_SH) use the same mechanism but different codes, because they count different units (D4).

A recall period that defines who belongs to a group — “employed in the last 12 months” versus “employed right now” — is a property of that group’s universe, not of the share indicator. It is recorded in CL_BRK_VAR.universe and the category’s definition_en, never by giving the indicator a different ref_period. POP_SH, POP_HH_SH and POP_HE_SH all carry ref_period = INTERVIEW, whatever recall period their breakdown’s universe uses.

4.3 Worked example: adding sector of employment

  1. Decide whose characteristic it is. “Sector of an individual’s main job” (EMP_SECTOR, describes IND) and “sector of the household head’s main job” (HHH_SECTOR, describes HHH) are two different variables. The first can break down only individual-level indicators; the second can break down household indicators such as the poverty rate.
  2. Register it in CL_BRK_VAR: describes = IND, applies_to_units = IND, universe = employed persons aged 15–64, classification = ISIC Rev.4, partition = Y, slot_order = 60.
  3. Register the categories in CL_COMP_BREAKDOWN: EMP_SECTOR_AGR for ISIC section A, EMP_SECTOR_IND for B–F and EMP_SECTOR_SER for G–U.
  4. Add a cut to TAB_PLAN.
  5. Produce the rows. When the cut is crossed with individual sex, the rows for women also carry SEX=F. When it is crossed with quintile, QUINT has the lower slot_order, so it takes slot 1 and EMP_SECTOR takes slot 2.

6 Metadata files

This section is the reference for every CSV under metadata/ and content/: what each file holds and which columns must be filled. Most of them are codelists (CL_*). A codelist is the list of valid codes for one column of the data file, with the meaning of each code. The rest are relations between codes (which qualifiers an indicator takes, which categories pair), rules the values must satisfy, registries (surveys, sources, boundaries, figures) and the plans of which cuts and series to produce.

The column tables in this section are generated from metadata/structure/COLUMNS.csv, the registry of every file’s columns, and the code tables from the codelists themselves (Section 11.1). In metadata 0.3.0 the columns added to the DSD file have these statuses: data_type, usage and relationship are C; measure_relationship, min_value and max_value are O. Every codelist’s last column, global_urn, is O. The DSD file’s position runs from 1 to 34, and its role list no longer has constant.

Rules for every CSV under metadata/ and content/:

  • UTF-8, comma-separated, one header row. Readers must open with utf-8-sig, because Excel’s “CSV UTF-8” writes a byte-order mark.
  • Multi-valued fields are space-separated.
  • No literal newlines inside a cell. Anything that needs paragraphs goes in a Markdown file (Section 10).
  • Column status: R required, C required when relevant, O optional.
  • Every codelist has these columns, plus the extra ones listed in its own subsection: code, name_en, definition_en, status (DRAFT, ACTIVE, DEPRECATED), version_added, replaced_by (C), notes (O).

6.1 Code rules

  • Uppercase ASCII letters, digits and _; start with a letter; at most 32 characters, the Stata variable-name limit. P-codes are used as issued and already comply.
  • _T and _Z are reserved sentinels and never appear as codes in a codelist CSV. The SDMX generator adds them as real codes, “Total” and “Not applicable”, to every codelist whose dimension admits them, as the sentinel column of DSD_AFW360_HH.csv says, each with the annotation AFW_SENTINEL = Y. The importer strips them again (D42, Section 3.4).
  • A code never changes meaning, and is never reused or deleted. A changed definition means a new code, with the old one DEPRECATED and replaced_by filled. Rewording a label is free.
  • Breakdown and qualifier categories are <var_code>_<category>. The whole code must still fit in 32 characters, so keep var_code short.
  • Indicator codes are <THEME>_<SUBJECT>[_<DETAIL>] and contain no poverty line, PPP round, welfare concept, COICOP division, unit or breakdown, because all of those are dimensions. Use POV_HC, never POV_HC_PL420.
  • Series ids are the indicator code, then its qualifier categories in slot order, then its defining category, joined by .: POV_HC.POVLINE_PL420.PPP_2021, CONS_SH.COICOP_CP01, POP_SH.EMP_SECTOR_AGR. Series ids are the only ids that contain a dot, and are therefore not SDMX code ids (see below). A series id is immutable once the series is ACTIVE (D13).
  • Source ids follow the code rules and are unique in SOURCES.csv, with one exception: they end in a run-version suffix _v<N>, whose lowercase v is the only lowercase letter allowed in any code. The recommended pattern is <ISO3>_<SURVEY>_<PROGRAM>_v<N>, for example SEN_EHCVM2021_LEGACY_v1.
  • In Stata, name the variable holding an indicator after its code in lower case, so no lookup table is needed.
  • Codes are also SDMX ids. Every code becomes an SDMX code id, which may hold only letters, digits, _, -, @ and $. The rules above are stricter, except for series ids. Series ids may contain ., which the SDMX IDType pattern for code ids forbids, so they are not SDMX code ids: SERIES_ID is an uncoded String attribute, and no codelist is derived from SERIES_PLAN.csv (D43). Artefact ids such as CL_SEX or DSD_AFW360_HH are NCNames: a letter, then letters, digits, _ or - (Section 3.1).
  • Codes follow global lists where one exists (D32). A code that matches a global code keeps or takes that code’s value where these rules allow, and records the global code’s full URN in global_urn (Section 3.8).

6.2 CL_INDICATOR.csv: the indicator dictionary

Beyond the common columns, the dictionary has the columns in Table 14. The dictionary describes what an indicator is: its population (stat_unit, universe_unit, universe_filter, numerator, weight), its statistic and reference period, its unit (unit_measure, with unit_denom, unit_time, price_basis and price_ref_year for levels and money), its plausible range, how the dashboard shows it (display_as, decimals, higher_is, short_name_en), its provenance in the microdata (source_questionnaire, source_vars, program) and its owner. Which qualifiers it takes is in INDICATOR_QUALIFIERS.csv (Section 6.14), and which rules its values must satisfy is in RULES.csv (Section 6.13); neither is a column of the dictionary any more (D18).

ref_period is an ISO 8601 duration (P7D, P12M, P3Y) or INTERVIEW; write P12M, never P1Y. unit_measure for money is always the placeholder LCU; the data row resolves it to the country’s currency (Section 2.6).

display_as fixes a defect the dashboard has today, where every value is formatted as a percentage. A share stored as 0.37 displays as 37.0%, and POV_NUM stored as 6520000 displays as 6.52 (millions).

Why the population fields matter. HHH_SEX_F means “people living in female-headed households” for a person-level poverty rate, and “enterprises in female-headed households” for an enterprise indicator. Without stat_unit, universe_* and weight, person-weighted and household-weighted numbers end up on the same chart. statistic matters too: a budget share can be the mean of household shares (MEAN) or the share of aggregate spending (RATIO_TOTALS), and the two differ.

6.3 CL_BRK_VAR.csv

Beyond the common columns (code is the var_code), the file has the columns in Table 15. describes says whose characteristic the variable is (IND, HHH for the household head, HH, HE); applies_to_units lists the stat_unit values it may break down; universe names the population its categories partition (Section 4.2); partition is Y when the categories are mutually exclusive and exhaustive; requires_qual lists qualifier variables the categories depend on, such as POVLINE PPP for POOR; slot_order fixes the slot the variable takes in a crossed row.

6.4 CL_COMP_BREAKDOWN.csv

Extra columns: var_code (R), parent (O, a category of the same variable, for nested classifications), order (R, display order). definition_en is required wherever the boundary is not obvious, such as age cutoffs, ISIC groupings and quantile ranking rules.

A category’s variable is always looked up through this var_code column, never inferred by parsing the code’s prefix: HE_ is a prefix of HE_COUNT_0, but that does not make it a category of a variable called HE.

6.5 CL_QUAL_VAR.csv and CL_QUALIFIER.csv

CL_QUAL_VAR extra columns: slot_order (R), requires (C, other qualifier variables that must appear with it, such as PPP for POVLINE), owner (R).

CL_QUALIFIER extra columns: var_code (R), value (C, the numeric parameter, such as 3.00 for POVLINE_PL300), basis (C, what that value is expressed in), order (R).

Which categories of one qualifier variable may appear with which categories of another is not a column of either codelist; it is a row of QUALIFIER_PAIRS.csv (Section 6.14, D18). When a category’s allowed set for some qualifier variable is _Z — as POVLINE_NPL’s is for PPP — that overrides the variable-level requires: a national-line row does not also require a PPP round, even though POVLINE otherwise requires PPP.

6.6 CL_GEO_SCHEME.csv and CL_GEO.csv

Schemes are parallel, not nested. ADM1 regions, ADM2 départements, Senegal’s zones and Guinea-Bissau’s agro-ecological zones are four different ways of cutting a country, and each is stored as its own set of units. Even where one scheme happens to group the units of another, as Senegal’s zones group its regions, nothing is derived from that nesting, and no scheme is required to decompose into another.

CL_GEO_SCHEME has one row per country and scheme, keyed ref_area + code (Table 16). has_geometry is Y only for ADM0 and ADM1 (Section 9.1). nests_in names another scheme only where nesting is genuine, for optional roll-up checks, never to derive geometry.

CL_GEO has one row per spatial unit (Table 17). Codes are P-codes for admin units (SN03, GW08) and <ISO2>_<SCHEME><nn> for other schemes (SN_ZONES01). The agro-ecological zones do not yet share one scheme name: Senegal’s are scheme ZONES (SN_ZONES01), Guinea-Bissau’s scheme AEZ (GW_AEZ01). One name for both is a pending metadata decision; until then the dashboard accepts either. valid_from and valid_to describe the boundary vintage the code belongs to, not the validity of the data; valid_to is empty while current.

The shapefiles in data_raw/shp/ already carry these P-codes: SN01 is Dakar, SN03 is Fatick, and GW08 is Bissau (the current tables call it SAB). Maps join on codes, never on names.

name_en “as issued by the boundary source” fits ADM0 and ADM1, but not zones or agro-ecological zones, which have no such source. For those schemes name_en is TBD until confirmed with the producer, and the boundary-sourced rule does not apply to them.

6.7 CL_AREA.csv

Extra columns: iso2 (R, the P-code prefix), currency (R, ISO 4217), wb_region (R).

Currency matters more than it seems. “FCFA” is two different currencies: XOF (CFA franc BCEAO, used in WAEMU, including SEN and GNB) and XAF (CFA franc BEAC). Eight AFW economies use neither. Monetary values in LCU are therefore not comparable across countries; comparison needs a PPP-denominated indicator.

6.8 Small codelists

Table 18 is generated from the codelist files themselves. _T and _Z are valid in SEX and AGE in addition to the listed codes (Section 2.2). CL_URBANISATION has a parent column: CAP and OU are children of U. The parent U is not itself produced by the current plan; a reader who wants urban as a whole aggregates CAP and OU by N_POP, which a legacy file cannot supply.

CL_STATISTIC also carries admits_se (R): Y when a value computed with this statistic can carry a standard error and confidence interval (as PROPORTION and MEAN do), N when it cannot; Table 4’ STD_ERR / CI_LOWER / CI_UPPER requirement reads this column. CL_UNIT holds the units of the dictionary; a data row’s UNIT_MEASURE is one of them or, for money, an ISO 4217 code registered as some country’s currency in CL_AREA.

6.9 SURVEYS.csv

One row per country and survey round (Table 19). status is DRAFT until a producer confirms the record and ACTIVE once confirmed, the same convention as a codelist’s. representative_levels is advisory metadata that the dashboard may display; it does not gate publication. analysis_units says which file each stat_unit is estimated from, so N_OBS is interpretable. Senegal’s row is the worked example: EHCVM 2021, fieldwork November 2021 to September 2022, national line 519.8 XOF per capita per day; the source says the line was “estimated using the EHCVM 2018 … in current prices”, so its price year is an inference and is recorded as one in notes.

6.10 Manifest

AFW360_HH_<ISO3>_<YEAR>_<ESTIMATION>_manifest.csv has two columns, key and value. The 17 keys are, in this order:

structure_id (WB.AFW360:AFW360_HH(0.3.0); equals every row’s STRUCTURE_ID), sdmx_csv_version (2.1.0), dsd_version, metadata_version, ref_area, time_period, estimation (CL_ESTIMATION; equals every row’s ESTIMATION), survey_id (the base survey, also for a model-based file), sources (the SOURCE_ID values that appear in the file, space-separated), file_name, n_rows, producer, program, software, run_timestamp (ISO 8601), status (DRAFT, SUBMITTED, VALIDATED, PUBLISHED), notes.

The manifest summarises the file; it holds nothing that a row needs. Precision is on each row (PRECISION), and the program run that produced each row is its SOURCE_ID, whose registry row carries the program version and inputs (Section 6.15). The source_type and precision keys of version 0.1.0 are gone (D15, D16, D17).

dsd_version is not chosen independently: the DSD is versioned with the metadata package, so it equals metadata/VERSION.

In version 0.3.0 the key dataflow became structure_id, the SDMX short reference to the dataflow and its version, and sdmx_csv_version was added (D46). The other 15 keys are unchanged. The manifest is a project-level sidecar, not an SDMX artefact: it describes a file (D43, D45).

TIME_PERIOD is the year the estimate refers to, which is not always a survey year. A microsimulated 2026 poverty rate has TIME_PERIOD=2026, ESTIMATION=MODEL, a source whose survey_id is SEN_EHCVM_2021, and OBS_STATUS=E on every row (Section 2.3).

6.11 TAB_PLAN.csv: which cuts are produced

A cut is one way of splitting the population, such as by residence, by region or by quintile. A row that lists two breakdowns is a crossed cut, such as quintile by sex of household head. TAB_PLAN is what turns the dictionary into a list of required rows (Section 2.7).

There is one row per cut, with the columns in Table 20. They give the codes used, not yes/no flags: geo_scheme is _T or a scheme code, urbanisation is _T or a set such as CAP OU R, sex and age are _T or sets of codes, comp_breakdowns lists breakdown variable codes in slot order, and themes is ALL or a list of theme codes.

The current plan (Table 21) reproduces the legacy Excel tables. The zone cut needs one row per country, because the two countries’ zone schemes differ. Share series add their defining breakdown to every cut they are produced for, which is why the data files hold crossed rows, such as sector of employment within quintile, that no single plan row names.

6.12 SERIES_PLAN.csv

plans/SERIES_PLAN.csv is the explicit list of series to produce (Section 2.7), with the columns in Table 22. A series is one row: its series_id (Section 6.1), the INDICATOR, the qualifier categories in MEASURE_QUALS, and, for a share indicator, the category it is a share of in DEFINING_BREAKDOWN, for example EMP_SECTOR_AGR for the series “share of employed persons working in agriculture”.

Three columns were added in metadata version 0.2:

  • name_en is the display name of the series, what a chart title or a report sentence says (D13). It is composed by default from the indicator’s short_name_en and the qualifier and category names, and a human overwrites it wherever the composed form reads badly. The dashboard shows name_en, never the id.
  • estimation lists the file kinds in which the series is expected: SURVEY, MODEL, or both space-separated (D17). Every series of version 0.1.0 has SURVEY.
  • status gains two values beyond DRAFT and ACTIVE (D23). On a row for a specific country, NOT_PRODUCED records that the country’s survey cannot support the series, and DEVIATES records that the country produces it under a definition that departs from the dictionary’s; both require notes. A country row overrides the ALL row for the same series_id (Section 2.7).

6.13 Verification rules: RULES.csv

Every rule that the validator applies to values is a row of metadata/rules/RULES.csv (D18). Rules used to be space-separated tokens in a column of the indicator dictionary; as a table they can be versioned, given a severity and a tolerance, and attached to a series rather than an indicator, without touching the dictionary.

A rule has a scope: DATAFLOW for a rule that applies to every row (scope_code empty), INDICATOR for every series of one indicator, or SERIES for one series. rule is one of the vocabulary below, param is its argument where it takes one, tolerance overrides the default absolute tolerance of Section 12 when filled, and severity is ERROR or WARN. The rule’s rule_id is <scope_code or AFW360_HH>.<rule>, followed by .<param> when the parameter is a qualifier variable; a numeric threshold is not part of the id, so AFW360_HH.RELIABILITY_MAX_CV keeps its id when the threshold changes.

Rule vocabulary:

  • RANGE_0_1, RANGE_NONNEG: bounds on OBS_VALUE.
  • AGG_SUM: over a population cut that is a partition, the children’s values sum to the parent’s.
  • AGG_NPOP_MEAN: the N_POP-weighted average of the children equals the parent.
  • AGG_BRACKET: the parent lies within the range spanned by its children; used where AGG_NPOP_MEAN cannot be computed, as in a legacy file with no N_POP.
  • SUM_TO_1_OVER, param a qualifier variable: the categories of that qualifier sum to 1, for example over COICOP.
  • SUM_TO_1_OVER_BRK: the categories of the series’ defining breakdown sum to 1.
  • MONOTONE_IN, param a qualifier variable: the value does not fall as that qualifier’s order rises, for example over POVLINE.
  • RELIABILITY_MIN_NOBS, RELIABILITY_MAX_CV, scope DATAFLOW, param the threshold: the two thresholds of the low-reliability rule (Section 2.6).

EQUALS_NPOP_RATIO of version 0.1.0 is retired: with N_POP defined as the denominator on a share row (D19), the category’s population is OBS_VALUE × N_POP by definition, so the rule checked nothing.

6.14 Relations: INDICATOR_QUALIFIERS.csv and QUALIFIER_PAIRS.csv

Two relations between codes live in their own tables under metadata/structure/ rather than packed into codelist cells (D18).

INDICATOR_QUALIFIERS.csv says which qualifier variables an indicator takes, one row per indicator and qualifier variable (Table 24). allowed is * for any category of the variable, or a space-separated list of the categories the indicator may use. An indicator with no row takes no qualifier. A row may also use a qualifier required by a breakdown it carries (Section 2.5), whether or not the indicator declares it.

QUALIFIER_PAIRS.csv says which categories of one qualifier variable may appear together with which categories of another, one row per category and partner variable (Table 25). allowed is a space-separated list of the partner’s categories, or _Z when the category takes none of them, which overrides the partner variable being requiresd.

6.15 Sources: SOURCES.csv

metadata/registries/SOURCES.csv registers every program run that has produced data rows, one row per source_id (D16). Every data row’s SOURCE_ID resolves to it.

kind is LEGACY_CONVERSION for a run of the converter over a legacy workbook, or PRODUCER for a producer’s own estimation program. The reliability columns of the data file are required on rows whose source is a PRODUCER run (Section 2.6). program_version is the git commit or release of the program, inputs names the files or datasets it read, with their inputs_sha256 where they are files in this repository, and run_date is when it ran. A new run of the same program on the same inputs is a new source with a higher _v<N>, not an edit of the old row; sources are append-only like every other registry.

7 What a producer delivers

This is the checklist for handing in a file. For each country and reference year, deliver:

  1. The key is the 19 columns FREQ through TIME_PERIOD. ACTION is R, FREQ is A, and OBS_VALUE is NaN on O and M rows (Section 2.6).
  2. Every required row (Section 2.7), including cells with no observations, each carrying its SERIES_ID, UNIT_MEASURE, OBS_STATUS, SOURCE_ID and reliability measures.
  3. A SOURCES.csv row for the program run, with its version and inputs (Section 6.15).
  4. The manifest (Section 6.10).
  5. Any metadata changes the data need, in the same pull request (Section 11).

7.1 Estimation rules

  • Code the indicator variable as missing for units outside its universe, so they leave both the numerator and the denominator.
  • Estimate with the survey design declared (weights, strata, PSUs), and use subpopulation estimation for groups rather than dropping observations, so that standard errors stay correct.
  • Use the weight named in the dictionary (POP = household weight × household size, for person-level statistics computed on household data).
  • Publish every estimate. Do not blank, round away or drop a small cell; report its N_OBS.
  • Write values unrounded, in base units.

7.2 A note on legacy conversions

Files that the converter produces from the legacy Excel inherit values already rounded to two decimals, and they carry no sample sizes. Their source in SOURCES.csv has kind = LEGACY_CONVERSION, and every row carries PRECISION (0.01 × scale, the workbook’s two decimals taken to base units). The validator widens its tolerances by each row’s PRECISION and does not demand STD_ERR, CI_*, N_OBS or N_POP on rows of such a source. This exemption belongs to the source kind, never to new production.

A cell already known to be wrong is withheld, not converted: its row is absent from the file, not present with a value or a comment. The exclusion is registered in LEGACY_OVERRIDES.csv (action WITHHOLD, with a reason and evidence) and subtracted from the required rows (Section 2.7, D5). Action COMMENT is different: the value is kept and OBS_COMMENT records why it is suspicious but worth keeping.

OBS_STATUS=O means “no value available” generally, not only “in the universe but no observations fell in this cell” (D9). On a row whose source is a legacy conversion, every O requires an OBS_COMMENT prefixed LEGACY_EMPTY:, explaining why the legacy sheet has no value for that cell.

7.3 How the dashboard shows reliability

Since nothing is suppressed, the dashboard carries the burden of honesty:

  • Every value is shown with its N_OBS, available on hover, in a details panel or in the downloaded table.
  • Charts show the confidence interval where one exists.
  • A cell flagged OBS_STATUS=U is visually de-emphasized rather than hidden, and the flag is set by the data, not by the dashboard (Section 2.6). OBS_STATUS=O renders as “no observations”, never as zero.
  • Displayed decimals are capped by the row’s PRECISION: a value converted from a workbook rounded to two decimals never shows more than those two accurate decimals in its display unit, however many CL_INDICATOR.decimals asks for elsewhere. This is the rule the dashboard must follow; the loader formats by display_as and decimals today, and capping by PRECISION is a later step.
  • Labels and formats come from the metadata, so that no chart, table or sentence composes a label or picks a format on its own: load_indicator_meta() gives each indicator’s display_as, decimals, higher_is and short_name_en, and each row carries its SERIES_ID and UNIT_MEASURE.

The loader. The dashboard reads only through the Python package afw360/ (D37); no chunk of index.qmd reads data_raw/. load_data(iso3, year=None, estimation="SURVEY") reads one SDMX-CSV file, checks its STRUCTURE_ID against metadata/VERSION, drops the three fixed columns and parses NaN; with year=None it takes the latest year’s file, it does not concatenate years. series(df, series_id, **dims) selects rows by exact equality and has no _T defaults: a single national value needs every breakdown dimension pinned to _T (GEO, SEX, AGE, URBANISATION, COMP_BREAKDOWN_1 to _5), otherwise it returns one row per value of the unpinned dimensions. load_text(iso3, slot) reads content/TEXT.csv, whose file column is relative to content/text/; load_figures(iso3) reads metadata/registries/FIGURES.csv, whose file column is relative to assets/figures/. load_boundaries(iso3, layer) reads the country’s GeoPackage (layers adm0 and adm1; file names differ in case, SEN_CODAB_v02.gpkg and GNB_CODAB_V01.gpkg) and renames its code column geo_code to GEO. Zone schemes are not yet named alike: the agro-ecological zones are scheme ZONES in Senegal and AEZ in Guinea-Bissau, and the dashboard accepts both. The deployment pins in the root requirements.txt include the Jupyter kernel packages (ipykernel, nbformat, nbclient), pyyaml and jinja2, which the render needs.

8 How to extend

Start here whenever you want to add something. Find the row in Table 30, edit the files it names, and bump the metadata version as shown (Section 11). Only one row changes the structure of the data file, and only the data team makes that change.

8.1 Add an indicator

  1. Search CL_INDICATOR for the same concept. If it exists, reuse it. Before creating a code, check whether the difference is a qualifier: a different poverty line, PPP round, welfare concept or COICOP division is never a new indicator. Neither is a population share; that is POP_SH, POP_HH_SH or POP_HE_SH with a breakdown, chosen by what the breakdown counts (D4).
  2. If a near-duplicate exists, fill related and related_note on both rows.
  3. Standardize the variables it needs in the harmonized microdata, so that the indicator is a plain aggregate of them (Section 1.4). Record them in source_questionnaire and source_vars, and the program that computes the indicator in program.
  4. Fill every R column and the C columns that apply.
  5. Register the qualifier variables it takes in INDICATOR_QUALIFIERS.csv, the rules its values must satisfy in RULES.csv, and each of its series in SERIES_PLAN.csv with a display name.
  6. Produce it for every applicable cut.
  7. Open a pull request (Section 11).

8.2 Add a breakdown variable

Follow Section 4.3: decide describes and applies_to_units, write the universe, reuse an international classification if one exists, set slot_order, register the categories, and add the cuts. Expect small N_OBS in fine groups, and publish them anyway with their sample sizes.

8.3 Add a qualifier variable

  1. Confirm it is a qualifier: the population behind each category is the same one (Section 1.1).
  2. Register it with a slot_order and, if it depends on another qualifier, requires.
  3. Register its categories, with value and basis where they apply, and their pairings with other qualifier variables in QUALIFIER_PAIRS.csv.
  4. Add a row to INDICATOR_QUALIFIERS.csv for every indicator that takes it, naming the allowed categories, and the new series to SERIES_PLAN.csv.

8.4 Add a country

Follow the order in Section 1.4: metadata first, data last.

  1. CL_AREA: add the country, with its ISO2 code (the P-code prefix) and its currency.
  2. CL_GEO_SCHEME: register every spatial scheme the country will publish, with the local name of each level.
  3. CL_GEO: register the units of each scheme, using the P-codes of the boundary file you will map with.
  4. Indicators: check each indicator in CL_INDICATOR against the country’s survey, and reuse the code wherever the definition holds. Where it does not, register a new code linked to the old one through related and related_note (Section 8.1). Never stretch an existing definition to fit.
  5. Breakdowns and qualifiers: map the survey’s own variable values to the shared codes, in the producer’s program. A country-specific category becomes a child of a shared code (a secondary-city stratum is parent = U), never an unrelated new code.
  6. SURVEYS: add each survey round, with its design, welfare aggregate and national poverty line.
  7. Boundaries: add the ADM0 and ADM1 boundary file and its GEO_SOURCES row (Section 9.4).
  8. TAB_PLAN: add rows only where the country’s cuts differ from the shared ALL rows, for example for its own zone scheme.
  9. SERIES_PLAN: add a country row for every series the survey cannot support (NOT_PRODUCED) or supports only under a different definition (DEVIATES), with the reason in notes.
  10. Data: register the program run in SOURCES.csv, produce the data file and manifest for each reference year (Section 7), run the validator, and open one pull request with the metadata and the data together (Section 11).

Every other code comes from the shared codelists.

9 Boundaries and figures

Every non-tabular asset follows the same pattern: a stable ID, a row in a registry carrying provenance, license and checksum, a path fixed by convention, and references by ID, never by path. Assets are never edited by hand; a wrong unit name, for example, is corrected in CL_GEO, not in the boundary file.

9.1 Maps exist for countries and ADM1 only

has_geometry = Y is set for ADM0 and ADM1. Every other scheme, including ADM2, zones and agro-ecological zones, is published as tables with no map, no geometry file and no missing-geometry error. Neither Senegal’s zones nor Guinea-Bissau’s agro-ecological zones therefore need polygons.

9.2 Storage

Boundaries are stored as GeoPackage (.gpkg) files, one per country per boundary vintage, with one layer per level:

geo/boundaries/SEN_CODAB_v02.gpkg     layers: adm0, adm1

Why not shapefiles: a shapefile is 5–6 files that must travel together. Its DBF field names are cut at 10 characters (the current files show cod_versio and adm1_ref_n), its text fields stop at 254 characters, its encoding is declared in a side-car .cpg, and its .prj carries no authority code (the current files say GCS_WGS_1984 with no EPSG number). A GeoPackage is one SQLite file with UTF-8 text, long field names, several layers and an SRS with its authority code, and geopandas, QGIS, ArcGIS and R all read it.

Rules:

  • Required layer fields: geo_code (matching CL_GEO.code), ref_area, scheme. A name column may be kept for convenience, but CL_GEO is authoritative, and disagreement is a warning, not an error.
  • CRS: EPSG:4326 in storage. Reproject only for display or area computation.
  • Hygiene: valid geometries, one feature per code, units covering the country exactly once. Geometry is built and checked with GEOS (sf::sf_use_s2(FALSE)), invalid rings repaired with st_make_valid(), from the plain (non-_em) shapefiles as the source — SN01 and SN13 fail s2/GEOS validity as issued.
  • Vintages are explicit. valid_from and valid_to in CL_GEO describe the boundary release a code belongs to, not the period the data cover. SEN’s COD-AB v02 dates from 2024 while the data are for 2021, and that is not an error.
  • Derived layers are generated, never hand-edited. Simplified display copies are planned for geo/derived/, which does not exist yet; once built, they may be rebuilt at any time, and the simplification tolerance is kept in the build script.
  • Size: keep files in git while they are small. Beyond a few MB, use Git LFS or an external store, with the URL and checksum in the registry.

GEO_SOURCES.csv columns: source_id, ref_area, provider, version, valid_on, url, download_date, licence, attribution (the credit line the map must show), crs, file, layers, sha256, status, version_added, notes.

9.3 Figures

Figures live at assets/figures/<ISO3>/<figure_id>.<ext> and are registered in FIGURES.csv, with columns figure_id, ref_area, time_period, theme, title_en, caption_en, alt_text_en (required: what a screen reader announces), indicators, source, producer, program, licence, file, sha256, status, version_added, notes.

Prefer generating figures from the data; an image is a last resort. Use SVG or PDF for charts, and PNG at twice display size for anything raster. The dashboard asks for a figure_id, not a file name.

11 Change control

This section says how a change gets into the database.

  • metadata/ and content/ live in git. Producers extend them on a branch and open a pull request, which the data team reviews.
  • Rows are append-only: no deletions, and no changing an existing code or its meaning. Deprecate instead.
  • Every merged change bumps metadata/VERSION (MAJOR.MINOR.PATCH, as shown in Table 30) and adds a line to metadata/CHANGELOG.md.
  • Version 0.x is pre-release (D24). While the major version is 0, a structural change is a minor bump, and all structural changes of a release are batched into one bump. Version 1.0.0 is declared when the first producer-delivered file passes the validator; from then on the “major” rule of Table 30 applies and a structural change needs a migration script and a major version.
  • A release bumps metadata/VERSION, runs the migration script under pipeline/migrations/<version>/ if the release is structural, and regenerates sdmx/ with pipeline/build_sdmx.R (Section 3.10). Every SDMX artefact carries that version. Once released, an X.Y.Z artefact is immutable; later edits go into the next version, never into a released one (D40).
  • Editing in FMR. Between releases, an artefact may be edited in FMR on a copy versioned <next>-draft. The export is re-imported into the CSVs with pipeline/import_sdmx.R and goes through a pull request like any other change (Section 3.11).
  • Every data file’s manifest records the metadata_version it was produced against.
  • The validator must pass before a pull request is merged or a file is published.
  • Editing a CSV in Excel is fine if you save as “CSV UTF-8” and check that codes have not been turned into numbers or dates. The byte-order mark that Excel writes is expected and is stripped on read.

Structural changes, meaning adding, removing or reordering a column of the data file or of a metadata file, are made by the data team only. They need a new DSD_AFW360_HH.csv or COLUMNS.csv, a migration script under pipeline/migrations/<version>/ that rewrites the existing files (D12), and the version bump of Table 30. DSD_AFW360_HH.csv itself has the columns position, id, component (dimension, time_dimension, measure, attribute), role (breakdown, reference, qualifier, measure, attribute, as in Table 4), name_en, codelist, data_type, usage, relationship, measure_relationship, required, sentinel, min_value, max_value and description. It has one row per component; the three fixed SDMX-CSV columns are not rows. The data-file header must equal the fixed columns followed by its id column, in order.

12 Validation checks (implemented in R)

This is the specification for the validator. Each check is phrased so that it can be implemented directly, and together they enforce every “must” in Sections 2 to 10.

The validator writes one findings file, a CSV with the columns check_id, severity (ERROR, WARN or INFO), file, row_key (C, empty for a file- or codelist-level finding) and message. The process exits with a non-zero status whenever the findings file holds at least one ERROR.

The validator is pipeline/validate.R (Rscript pipeline/validate.R --root . --out <findings.csv>). It loads its modules from <root>/pipeline/R, so a scratch copy of the repository used as --root must contain pipeline/ as well as metadata/ and data/ (and content/, assets/, geo/ and sdmx/ for the checks on those folders). Check ids are <MODULE>.<NAME>; a module that fails outright reports <MODULE>.CRASH. STRUCT.* findings name the file as data/<stem>.csv even when --data points elsewhere. The validator needs DSD_AFW360_HH.csv: the key and data columns are read from it (18 dimensions plus TIME_PERIOD; the three fixed columns plus 34 components), never hard-coded. On the 0.3.0 data it reports no ERROR; the 42 CODES.DRAFT warnings come from manifests still marked DRAFT.

Structure

  • The header is the three fixed columns followed by the DSD components, exactly: same names, same order (after stripping a BOM) (STRUCT.HEADER).
  • The file name is AFW360_HH_<REF_AREA>_<TIME_PERIOD>_<ESTIMATION>.csv, and every row’s REF_AREA, TIME_PERIOD and ESTIMATION equal the name’s and the manifest’s.
  • No dimension or qualifier cell is empty.
  • The key, meaning the 18 dimensions and TIME_PERIOD together, is unique.
  • STRUCTURE is dataflow (STRUCT.STRUCTURE), STRUCTURE_ID is WB.AFW360:AFW360_HH(<VERSION>) with the version in metadata/VERSION (STRUCT.STRUCTURE, and SDMX.CSV_HEADER), ACTION is R (STRUCT.ACTION) and FREQ is A on every row (FREQ is checked against CL_FREQ through CODES.UNKNOWN). The earlier STRUCT.DATAFLOW check is gone with the DATAFLOW column.
  • STRUCT.ATTR_LEVEL (ERROR): across all data files, SERIES_ID has one value per combination of INDICATOR and the ten breakdown and qualifier dimensions, and UNIT_MEASURE one value per REF_AREA and INDICATOR (Section 3.2). The finding’s file is the first file holding the group, and its row_key is the attribute id plus the group’s values.

Codes

  • Every code exists in its codelist. Newly produced rows use ACTIVE codes; existing rows are valid against any code that is not DRAFT. valid_from / valid_to are compared against the manifest’s run_timestamp, never against TIME_PERIOD.
  • GEO belongs to REF_AREA, and its scheme is registered for that country. An ADM0 code is registered in CL_GEO for building the country outline, but is rejected wherever it appears in the GEO breakdown column of a data row; a national row writes GEO=_T.
  • Breakdown slots are filled from the left in canonical order, with no variable twice, and unused slots are _T.
  • Qualifier slots follow the same rules, and unused slots are _Z.
  • SEX and AGE are _Z when the indicator’s stat_unit is not IND, and _T or a code otherwise.
  • Breakdown variables are compatible with the indicator’s stat_unit.
  • Every qualifier used is declared for the indicator in INDICATOR_QUALIFIERS.csv, with the category among its allowed, or is required by a breakdown in the same row.
  • QUALIFIER_PAIRS.csv pairings hold, for example POVLINE_PL420 only with PPP_2021.
  • SERIES_ID exists in SERIES_PLAN.csv, and the row’s INDICATOR, its qualifier categories and, for a share series, its defining category equal the plan row’s.
  • UNIT_MEASURE equals the indicator’s unit_measure, or, where that is LCU, the currency of the row’s REF_AREA in CL_AREA; a code outside CL_UNIT_MEASURE is CODES.UNIT.
  • CODES.DRAFT resolves DRAFT status through the derived codelists and, for SERIES_ID, through the SERIES_PLAN.csv status.
  • SOURCE_ID exists in SOURCES.csv, with the row’s REF_AREA, and is listed in the manifest’s sources.
  • No code in any codelist starts with _; _T, _Z, _U, _O and _X are the only values that do.

Coverage

  • The rows equal the set defined in Section 2.7: nothing missing, nothing extra. The set is built from the series whose estimation includes the file’s ESTIMATION, taking a country row of SERIES_PLAN over the ALL row, and leaving out series with NOT_PRODUCED for the country.
  • Nothing listed in excluded_breakdowns appears.
  • A SURVEYS row and a manifest exist, and the manifest matches the file: estimation, n_rows, file_name, and sources equal to the distinct SOURCE_ID values in the file. For a SURVEY file the survey’s time_period equals the file’s; for a MODEL file it is the base survey’s year and is not compared.
  • The manifest’s structure_id equals WB.AFW360:AFW360_HH(<VERSION>) and its sdmx_csv_version is 2.1.0 (COVER.MANIFEST, row keys key=structure_id and key=sdmx_csv_version). COVER.FILE_MISSING takes the estimations it expects from the effective SERIES_PLAN.csv estimation column (NOT_PRODUCED excluded, SURVEY when nothing else applies).
  • Conversely, for every SURVEYS.csv row a SURVEY data file and manifest exist for that country and year. A missing file is a WARN, not an ERROR, because metadata precedes data (Section 1.4); without it the validator would be silent about a whole country, since every other coverage check runs only over files that exist.

Values

  • OBS_VALUE is numeric and within valid_min / valid_max.
  • OBS_VALUE is NaN exactly when OBS_STATUS is O or M, and never empty (D39). VALUE.NUMERIC accepts NaN; VALUE.STATUS_EMPTY is an error on NaN or empty under a status other than O or M, and on a number under O or M. Not yet enforced: an empty OBS_VALUE on an O or M row is still accepted as missing (the coverage tests build such rows); the published files use NaN. The rules of RULES.csv see a NaN value as missing, and the STD_ERR and interval requirement does not count NaN as filled.
  • The mandatory attributes SERIES_ID, UNIT_MEASURE, OBS_STATUS and SOURCE_ID are never empty.
  • N_OBS_NUM, DEFF and DF are empty or non-negative, N_OBS_NUM and DF are integers, and N_OBS_NUM is at most N_OBS (VALUE.N).
  • STD_ERR ≥ 0 and CI_LOWER ≤ OBS_VALUE ≤ CI_UPPER.
  • N_OBS is a non-negative integer and N_POP is non-negative. Both are present, and STD_ERR with its interval where the statistic admits one, on every row whose source has kind = PRODUCER; they may be empty on rows of a LEGACY_CONVERSION source (Section 7.2).
  • N_OBS = 0 implies OBS_STATUS = O.
  • PRECISION is empty or a positive number, and is filled on every row of a LEGACY_CONVERSION source.
  • OBS_STATUS follows the precedence of Section 2.6: E on every filled row of a MODEL file and on no row of a SURVEY file; D on every filled row of a series whose country status is DEVIATES and on no other; U exactly where the reliability thresholds of RULES.csv are breached and no higher code applies; Q nowhere.

Verification rules from RULES.csv

  • AGG_SUM: children sum to the parent over a partition.
  • AGG_NPOP_MEAN: the N_POP-weighted average of the children equals the parent, within ±2h (the weighted mean of rounded children is off by at most h, and the parent by h). It needs each child’s N_POP; where a legacy file cannot supply that, AGG_BRACKET is used instead — the parent’s value falls within [min(children) − h, max(children) + h]. Checked against every mean/share series in both countries, AGG_BRACKET holds with zero violations; only POV_NUM-style totals fail it, as expected of a total rather than a mean.
  • SUM_TO_1_OVER:<QUAL_VAR> and SUM_TO_1_OVER_BRK: the categories sum to 1.
  • MONOTONE_IN with param = POVLINE: the value does not fall as the line rises; no tolerance applies.
  • RANGE_0_1, RANGE_NONNEG.
  • A rule with scope INDICATOR applies to every series of the indicator; with scope SERIES, to that series only; with scope DATAFLOW, to every row. The rule’s severity is the finding’s severity.
  • Tolerances. Let h = PRECISION / 2 for a row with PRECISION filled, and h = 0 otherwise, so an exact value must match exactly. A single value matches within ±h. A sum of k children against a parent (AGG_SUM) matches within ±(k+1)h, using the largest h among the rows compared. A closure over k categories (SUM_TO_1_OVER…) matches within ±k·h — for the 13 COICOP divisions of a legacy file, ±0.065, against an observed range of 0.96–1.02. A rule row’s tolerance, when filled, replaces the computed bound. Every comparison is abs(dev) <= tol + 1e-9, so floating-point noise at the boundary never fails a valid value.
  • Partial category sets. When a partition’s full set of categories is not all present in the file, a closure or sum check is skipped with an INFO finding rather than run against a partial set. When a required category is present but carries no value (O) or is withheld, the check cannot run either and is skipped with a WARN, so that an unverifiable aggregation stays visible without counting as a failure.
  • The parent of a row is the same series’ row for the cut with that breakdown set to _T, found through the row’s provenance — the series_id, cut_id and defining breakdown kept from SERIES_PLAN/TAB_PLAN generation (Section 2.7) — not guessed from the codes in general. Where the breakdown required a qualifier the series does not declare (POOR requires POVLINE), that qualifier is therefore _Z in the parent.
  • Children’s N_POP sums to the parent’s for any partition = Y breakdown that is a population cut of the row, within floating-point noise only (1e-9 × |parent| + 1e-9), since population counts are never rounded. The check never runs over a series’ defining breakdown, where every child’s N_POP is the same denominator (D19).

SDMX

The module pipeline/R/validate_sdmx.R holds six checks, specified in Section 3.10:

  • SDMX.STALE (ERROR): the files under sdmx/ are not stale; the same property as pipeline/build_sdmx.R --check exiting 0 (D28).
  • SDMX.XSD (ERROR): the structure message is valid against the vendored SDMX-ML 3.1 XSDs.
  • SDMX.URN (ERROR): every reference inside the message resolves, sub-agencies are declared, and the semver dependency rule holds.
  • SDMX.IDENT (ERROR): agency, version, id and English name of every maintainable.
  • SDMX.CSV_HEADER (ERROR): every data file’s header is the 37 data columns and every STRUCTURE_ID names the current version.
  • SDMX.SKIPPED (INFO): the root has no sdmx/ folder, so SDMX.XSD, SDMX.URN and SDMX.IDENT report nothing.

Deterministic output

  • Every file the pipeline writes is byte-identical across runs on the same inputs: rows sorted by the 19 key columns (Table 4, FREQ through TIME_PERIOD) in DSD order. The exception is pipeline/build_geo.R: the GeoPackages it writes under geo/boundaries/ are not byte-deterministic, so regenerating them changes the files and the sha256 fields it records in GEO_SOURCES.csv; the committed GeoPackages and hashes are the reference (WP11), and a deterministic writer is a later patch release with a migration.
  • UTF-8 with no byte-order mark, LF line endings.
  • A missing value is written as an empty string, never NA. The one exception is OBS_VALUE on an O or M row, which is NaN (Section 2.6).
  • Numbers are written in fixed notation, never scientific, rounded with round(x * scale, 10) and a fixed formatter, with no trailing zeros.
  • run_timestamp is an injectable parameter, so a test run can reproduce a fixed manifest.

Assets

  • Every geo_code in a geometry layer exists in CL_GEO with the same ref_area and scheme.
  • Every CL_GEO code whose scheme has has_geometry = Y has a geometry; schemes with N are skipped.
  • Geometries are valid, unique per code, and in EPSG:4326.
  • Every registry row points at a file that exists, with a matching sha256.

Text

  • Every {…} reference is reported as a WARN until the reference syntax is settled (open decision 10); resolving each one to exactly one observation is deferred to the dashboard switch-over.
  • Exactly one of body and file is filled, and referenced files exist.
  • Every slot the dashboard requests exists for the country and year, or inherits from ALL. Deferred with content/SLOTS.csv to the dashboard switch-over (Section 10.1); until then no slot registry exists to check against.

Metadata files

  • COLUMNS.csv (Section 6) is the column registry this section checks against: every file’s header and required columns are read from it, not hard-coded in the validator.
  • Codes are unique and follow Section 6.1.
  • Every R column is filled, except that TBD is accepted there in place of a value, and only on a DRAFT row: a warning while the row is DRAFT, an error once it is ACTIVE.
  • A DRAFT code is valid only inside a file whose own manifest declares status = DRAFT (a warning otherwise); DRAFT codes may still be renamed, and the “a code never changes meaning” rule (Section 6.1) starts to apply only from the row’s first ACTIVE version.
  • Every var_code, parent, replaced_by, source_id, scheme and nests_in reference resolves, and every CL_AREA.currency is a code of CL_UNIT_MEASURE (META.REFERENCE).
  • META.ARTEFACTS: ARTEFACTS.csv has exactly 32 rows, lists every CL_*.csv, has no duplicate id, and every source_file it names exists.
  • META.GLOBAL_URN: every filled global_urn is a full code URN, urn:sdmx:org.sdmx.infomodel.codelist.Code=<agency>:<id>(<version>).<code>.
  • slot_order values should be unique within CL_BRK_VAR and within CL_QUAL_VAR. A tie is a warning, not an error, and is broken alphabetically.
  • Every RULES.csv row has a known rule, a scope_code that resolves to an indicator or a series, a param where the rule takes one, and a severity; the two reliability thresholds exist exactly once each with scope DATAFLOW.
  • Every INDICATOR_QUALIFIERS.csv row names an indicator and a qualifier variable that exist, and every listed category belongs to that variable. Every QUALIFIER_PAIRS.csv row names a category, a partner variable and partner categories that exist.
  • Every SERIES_PLAN.csv row has a name_en, an estimation of SURVEY, MODEL or both, and a status among DRAFT, ACTIVE, NOT_PRODUCED and DEVIATES; the last two appear only on country rows, with notes filled, and every country row has an ALL row with the same series_id. Its series_id equals the id composed from its indicator, qualifiers and defining category.
  • Every SOURCES.csv row has a kind, a survey_id that resolves, a program and a program_version; where inputs are files in the repository, their inputs_sha256 match.

13.2 Open decisions

  1. Age cutoff for household heads. The current Youth_HH / Older_HH boundary is undocumented; confirm it before publishing any HHH_AGE_* code.
  2. Quintile definition. National or within-area ranking, person- or household-weighted. The answer goes in CL_BRK_VAR.definition_en.

  4. GNB survey metadata — closed by D6. EHCVM 2021/22 maps to TIME_PERIOD 2021, survey_id GNB_EHCVM_2021 (user-confirmed; About_GNB.txt remains a placeholder with no real survey metadata).
  5. Where large binaries live. Git, Git LFS, or an external store referenced from GEO_SOURCES.csv.
  6. Boundary vintage policy. Who decides when to adopt a new COD-AB release, given that P-codes can change and older data must still resolve.
  7. Where variable-level metadata lives. Section 1.4 asks for documentation of every harmonized microdata variable behind an indicator. CL_INDICATOR names those variables but has nowhere to describe them. A variable dictionary per survey, kept with the producer programs or under metadata/, is the obvious candidate.
  8. A country that cannot produce an indicator — closed by D23. A country row in SERIES_PLAN.csv with status = NOT_PRODUCED removes the series from that country’s required rows; DEVIATES keeps the rows and marks them OBS_STATUS=D (Section 6.12).
  9. The Departement sheet — closed by D3. The sheet is skipped entirely: all 82 of its labels are marked SKIP in LEGACY_LABELS.csv (see Annex 2).
  10. Reference syntax for live numbers. Section 10.2 is a sketch. It does not yet say how a reference names several qualifiers, or confirm that PL420 is shorthand for POVLINE_PL420. Since D13, a series_id such as POV_HC.POVLINE_PL420.PPP_2021 names a series unambiguously and is the natural reference key; the syntax is settled at the dashboard switch-over.
  11. A model-based value that also fails the reliability rule. One row carries one status code, and E takes precedence over U (D22), so the reliability flag is lost on such a row and only the standard error shows it. If nowcasts with small-cell uncertainty become common, a separate reliability attribute may be warranted.
  12. Series ids as SDMX code ids, closed by D43. Series ids contain ., and the SDMX IDType pattern for code ids allows only letters, digits, _, -, @ and $. The data lead chose on 2026-09-29 to keep the dotted ids unchanged in the data files: SERIES_ID is an uncoded mandatory String attribute, no codelist is derived from SERIES_PLAN.csv, and the project validator checks every value against that file (Section 6.1).

Annex. Mapping the current tables

Read this if you are writing the converter. It maps every label and column of the current Excel tables to the new codes.

The full mapping lives in three files under metadata/plans/, all seeded from pipeline/bootstrap/seeds/label_triage.csv (D11): LEGACY_LABELS.csv maps each indicator label to its INDICATOR and qualifiers, or to action SKIP; LEGACY_COLUMNS.csv maps each column to its breakdown dimensions; LEGACY_OVERRIDES.csv registers withheld or commented cells (D5). They must cover all four sheets, including the Departement sheet’s raw-variable labels (npoor300, npoor420, (max) con_1 … con_15, (max) ext_emp), all marked SKIP (D3).

Annex 1. Indicators

Where a legacy label’s weight, statistic or unit_time cannot be read off the label alone — every HE flow indicator, such as HE_PROFIT and EN_ELEC_SPEND — CL_INDICATOR records the best guess with notes: LEGACY assumed, and the row stays DRAFT until a producer confirms it.

Annex 2. The Departement sheet

The sheet exists only for Senegal, and the converter skips it entirely, for all 82 of its labels (D3). Despite its name it holds the same 14 regions as the ADM 1 sheet (findings, 6.1), so loading it alongside ADM 1 would produce rows with the same key. Most of those keys carry conflicting values: the sheet’s poverty totals disagree with ADM 1 (4.13M/7.88M poor at $3.00/$4.20 vs 3.13M/6.52M), and several of its “shared” indicators are impossible on their face (HE has any credit access = 1.00 in all 14 regions; HH has 4+ HE = 0.80–1.00 — see input-tables-findings.qmd §6.1). LEGACY_LABELS.csv records this with action SKIP on all 82 of the sheet’s rows.

Annex 3. Columns to dimensions

The mapping from current Excel columns to new dimensions no longer lives in this document as a fixed list; it lives in LEGACY_COLUMNS.csv under metadata/plans/, seeded from pipeline/bootstrap/seeds/label_triage.csv (D11).

14 Changes since v0.5

Version 0.6 of the standard and version 0.3.0 of the metadata make the database conform to SDMX 3.1. The data lead took D27 to D37 on 2026-09-29; D38 to D46 are the design decisions that carry them out. The final pass of v0.6 records what the implementation established: FMR 12.4.2 is installed and loads the SDMX-ML 3.0 profile once the agency WB is registered (Section 3.11); the validator’s SDMX.* checks and the new STRUCT.*, CODES.*, META.* and VALUE.* checks (Section 12, Section 3.10); the counts of the structure message (82 concepts, 22 codelists with 299 codes, 57 MSD children); the MSD model and the quoting of the metadata messages (Section 3.6); the full-URN form of SDMX_CROSS_DOMAIN_CONCEPT (Section 3.5); the dashboard loader (Section 7.3).
